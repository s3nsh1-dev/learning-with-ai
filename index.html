Give your containers a home.

A server is a computer that runs your app and accepts requests. In this example, you rent a Linux machine with a public IP address. It stays on when your laptop is off.

Deployment puts a version of your app on that server and starts it. You build Docker images, upload them to an image registry, then have the server download them and run containers.

Compose can start the services there. You supply production settings and secrets, persistent database storage, and network access to the proxy's public ports.

1

Find the address

DNS tells the browser where to go.

A domain name such as myapp.com is a memorable name. DNS, the Domain Name System, lets the browser look up an IP address for it. A cached answer can save a fresh lookup.

myapp.comDNS lookup →203.0.113.10

Illustrative IP address, reserved for documentation.

For this setup, you configure an A record pointing to the server's public IPv4 address. An AAAA record serves the same purpose for IPv6.

DNS supplies the address. It does not send the web request onward or choose between / and /api/tasks.

Reference: MDN on DNS and web requests.

2

Secure the connection

HTTPS protects the trip across the internet.

The https:// in the URL tells the browser to use a secure connection. It normally contacts port 443. A port identifies which service to reach at an IP address.

HTTPS is HTTP protected by TLS. TLS encrypts traffic and detects tampering. The server presents a certificate, and the browser checks that it is trusted and valid for the domain as it establishes the secure connection.

The encrypted connection ends at the proxy.

The proxy decrypts the request so it can read and route it. Our example uses HTTP from there to the containers. Encrypting that second connection requires its own TLS setup.

Caddy can obtain and renew certificates automatically when its domain and certificate validation are configured correctly. Nginx can also handle HTTPS with certificates you configure.

Reference: Caddy's automatic HTTPS documentation.

3

Choose a service

The reverse proxy routes the request.

A reverse proxy accepts requests on behalf of your app. It reads the requested hostname and path, then forwards the request according to your routing rules. The browser keeps using the public URL.

These rules preserve the path. Inside their shared Docker network, containers can find each other using service names such as web and api. The visitor's browser cannot resolve those private names.

In this setup, only the proxy publishes web ports. The app ports and database stay private. DNS points to the server; the proxy handles the choice of container.

References: Compose networking and Caddy request forwarding.

4

Draw the page

The response completes the round trip.

The web container sends HTML back through the proxy. The browser loads the CSS and JavaScript too. In our task app, that JavaScript runs in the visitor's browser and asks for data:

const response = await fetch("/api/tasks");
const tasks = await response.json();

The relative path uses the current site, so the request goes to https://myapp.com/api/tasks. The proxy forwards it to the API, which reads the database and returns JSON.

API→Proxy→ HTTPS →Browser

The browser uses those tasks to update the screen. Your API code ran on the server. The JavaScript drawing this task list ran on the visitor's device.

Why doesn't the browser call localhost:8000?

In browser JavaScript, localhost means the visitor's own computer. It would look for an API there. Use your public API URL, or a relative path such as /api/tasks when your proxy routes API requests on the same site.

The next deployment

New containers. The same public URL.

Editing code on your laptop leaves the server running the deployed version. To release a change, build a new image and update the server's containers.

CI/CD automates checks and delivery. A pipeline can test the code, build and upload the image, then update the server. Delivery can include a human release step; continuous deployment makes release automatic.

If the server address and routing stay the same, the visitor still opens https://myapp.com.
