First, can the request get in?

Your laptop opens the page, but your phone cannot. Change where the port is published and watch the connection.

Being on the same Wi-Fi does not guarantee that a phone can reach a server. The server also needs to listen on an address reachable from that network.

127.0.0.1 is IPv4 loopback: it leads back to the device using it. ::1 does the same for IPv6. Your phone’s localhost is your phone, not your laptop. A laptop’s Wi-Fi address, such as 192.168.1.12, is a different way in.

Compare the listening addresses side by side

In this project, Vite listens on [::1]:5173. For a normal Docker bridge network, publishing 8081:80 uses all host addresses by default. Publishing 127.0.0.1:8082:80 limits that mapping to IPv4 loopback. The two services can therefore behave differently on the same laptop.

A reachable bind address is only one requirement: routing, Wi-Fi client isolation, and firewall settings still affect access. See Docker’s port publishing reference for configurable defaults and networking exceptions.

Suppose the laptop opens a service at 127.0.0.1:8082. Would using the laptop’s Wi-Fi address on your phone reach that same mapping?

Reveal the reasoning

No. Changing the address in the browser does not change where Docker publishes the port. The mapping must include a reachable host address.

Why specify loopback in the Compose file?

Your laptop can move between networks while its Compose settings stay the same. A loopback mapping expresses that a service is intended for access from this host.

Then, where does the image go?

The API waits for requests. The collector runs a different command from the same codebase: it periodically asks the upstream feed for new radar images. This kind of background process is often called a worker.

They are separate containers, so their private filesystems are separate too. Writing a file inside the collector does not automatically make it appear inside the API.

The shared bind mount supplies the handover:

# Under both api and collector:
volumes:
  - ./frames:/var/lib/rainfall/frames

The left side names one host directory. The right side is where each container sees it. Repeating the same source directory gives both processes access to the same files.

Compare shared and separate storage

Both containers use /var/lib/rainfall/frames, but one mounts ./frames-a and the other mounts ./frames-b. Do they share images?

Reveal the reasoning

No. The paths inside the containers match, but the host directories differ. Sharing depends on the source storage.

Sharing a directory also needs a file-writing agreement. For example, the collector can finish a download in a temporary file, then rename it into place on the same filesystem. That prevents the API from reading a half-written image.

Why repeat the code mount and other service settings?

A separate worker can prevent slow collection work from occupying request handlers and avoids automatically starting another collector for every API replica. A web server can also run background tasks; separation is an architectural choice, not a requirement.

Why do simpler tutorials often use separate volumes?

Requests and files now have a route. But before either process starts, Compose must resolve the values in its configuration.

Before startup, where do the values go?

Your question was: how can ${WEB_PORT} work without an env_file: entry? The answer is that Compose configuration and a container’s environment have separate sources.

For a typical command run in the project directory, Compose automatically reads .env for substitution. Shell variables take precedence; --env-file can select a different file. A service’s env_file: instead supplies variables for its container.

Give the same name two different values and the distinction becomes visible. Assume the shell does not override WEB_PORT:

# .env
WEB_PORT=4000

# .env.web
WEB_PORT=9999

# compose.yaml (app listens on port 8000)
services:
  web:
    image: your-web-image
    env_file: .env.web
    ports: ["${WEB_PORT}:8000"]

Predict the result: is the host port 4000 or 9999?

Reveal the reasoning

4000. Compose substitutes ${WEB_PORT} from .env. Inside the container, WEB_PORT is 9999. That variable only affects the app if its code reads it.

See the two values in the resolved Compose output
What if the interpolation variable is missing?

Without a shell value, file value, or default, Compose warns and substitutes an empty string. What happens next depends on where the blank lands. In a port mapping it can leave the host port unassigned, allowing Docker to allocate one dynamically; other fields may become invalid.

For a required value, write ${WEB_PORT:?Set WEB_PORT} so configuration fails with a useful message. Use docker compose config to inspect the resolved model before starting the app.

The distinction to keep is where the value goes. .env can supply values used in your Compose file. It does not automatically put every variable into a container. env_file: supplies the service’s environment. Docker documents interpolation sources and container environment settings separately.

Read the file by following a connection

When a line feels mysterious, point to its two ends. A published port connects a host address to a container port. A bind mount connects a host directory to a container path. A variable source supplies a particular configuration value.

Then ask what would break if that connection changed. That question tells you why the line exists.
