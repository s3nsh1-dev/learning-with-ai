Docker Compose · Part 2 of 2

Writing the file yourself, field by field

Part 1 explained why the file exists. This part writes one. The stack is the same web application and PostgreSQL database, except that the web service is now built from your own code rather than pulled ready-made, which is what a real project looks like.

Every key is introduced by the problem it solves, and every result on this page was produced by running this exact stack on your machine, including the failure in Section 4.

How to read the colours: every key answers one of three questions

What is it made of?image and build. Where the contents of the container come from.
What is it connected to?ports, volumes, environment, env_file. Everything crossing the container’s edge.
When does it run?depends_on, healthcheck, restart. Start-up order, and what happens on failure.

Section 1 · The shape of a service

Three questions every service answers

A compose file looks like a long list of unrelated keys, and that is what makes it hard to write from memory. It becomes easier once you notice that a service definition only ever answers three questions, and that every key you will meet belongs to one of them.

Keep this grouping in mind and the rest of this page is only detail. When you sit down to write a service, work through the three in order: what is it made of, what is it connected to, and when should it run.

The file you will have finished by the end of this page

name: notes-api

services:
  web:
    build: .
    ports:
      - "8080:8000"
    environment:
      DATABASE_URL: postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
    volumes:
      - ./app:/app
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    env_file:
      - .env
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
      interval: 3s
      timeout: 3s
      retries: 10
      start_period: 5s
    restart: unless-stopped

volumes:
  pgdata:

The colours follow the three questions, not the syntax. Read down the web service and the shape is visible: one line saying what it is made of, four keys wiring it to the outside, then two controlling when it starts. Three other files sit beside this one: Dockerfile, .env, and app/app.py. Section 3 explains why .env is doing two different jobs at once.

Section 2 · What it is made of

image: for software someone published, build: for yours

These two keys answer the same question, and you pick exactly one. image: names an image that already exists and Compose pulls it. Databases, caches and message brokers are almost always this: you are not writing PostgreSQL, so you take it as published.

build: points at a folder containing a Dockerfile and Compose asks the daemon to build an image from it. Your own application is almost always this, because there is no published image of code you wrote this morning.

The value in build: . is not the Dockerfile. It is the build context: the folder handed to the daemon, which is both the root for every COPY in the Dockerfile and the place the Dockerfile itself is looked for. Writing . means “the folder this compose file is in”.

Proof that up on its own will not rebuild

$ docker image inspect notes-api-web:latest --format '{{.Id}}'
sha256:dc5b14702fcc

$ grep BANNER app/app.py          the source was edited after that build
BANNER = "Notes API v2, edited on the host"

$ docker compose up -d          no --build
 Container notes-api-db-1   Started
 Container notes-api-web-1  Started
$ docker image inspect notes-api-web:latest --format '{{.Id}}'
sha256:dc5b14702fcc       ← identical. The edit was never built in.

$ docker compose up -d --build
 Image notes-api-web Built
 Container notes-api-web-1  Recreated
 Container notes-api-web-1  Started
$ docker image inspect notes-api-web:latest --format '{{.Id}}'
sha256:701785809bb3       ← a new image. Only web was recreated; db was left alone.

This is the most common “why is my change not showing up” in Compose. The rule is short. If the change is in a file that COPY put into the image, you need --build. If the change is in a folder you bind-mounted, you do not, which is the subject of the next section.

Section 3 · What it is connected to

Ports, volumes, and settings from outside

Three keys, each opening a different kind of hole in the container’s edge. Part 1 and its follow-up covered ports: in detail, so one reminder is enough here: host on the left, container on the right. When you are unsure, docker compose config prints the parsed file with both sides named.

$ docker compose config
    ports:
      - mode: ingress
        target: 8000          the port inside the container
        published: "8080"     the port on your machine

Getting the order backwards produces a confusing symptom rather than an error. With "8000:8080" on a service that listens on 8000, a connection to localhost:8000 is accepted and then dies, because the host side is wired to container port 8080 where nothing is listening. curl reports exit 56 rather than “connection refused”, and docker compose ps gives it away with 80/tcp, 0.0.0.0:8000->8080/tcp: the real port sitting there unpublished.

Volumes: two different things sharing one key

The volumes: key accepts two kinds of entry that look almost identical and behave nothing alike. What separates them is the left-hand side: a path starting with . or / is a bind mount, and a bare word is a named volume.

The bind mount, demonstrated

$ curl -s localhost:8080
Notes API v1

$ sed -i 's/Notes API v1/Notes API v2, edited on the host/' app/app.py
edited on your machine. No rebuild, no restart, no docker command at all.

$ docker compose exec web grep BANNER /app/app.py
BANNER = "Notes API v2, edited on the host"     the container already sees it

$ docker run --rm notes-api-web:latest grep BANNER /app/app.py
BANNER = "Notes API v1"                       the image still holds the old copy

Both results are correct at the same time, and that is the whole idea. The image is a fixed, shippable snapshot; the bind mount lays your live folder over the top of it while you work. In production you drop the mount, and the container runs what the image contains.

Settings: environment, env_file, and the .env that is neither

Three things with confusingly similar names. environment: lists variables inline, and env_file: reads them from a file. Both put variables inside the container. The third is different: a file literally named .env, sitting beside your compose file, which Compose reads for its own use to fill in any ${...} before it parses the file.

# the compose file, before Compose has read it
    environment:
      DATABASE_URL: postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}

$ cat .env
POSTGRES_USER=notes
POSTGRES_PASSWORD=secret
POSTGRES_DB=notes

$ docker compose config          what Compose actually resolved
  web:
    environment:
      DATABASE_URL: postgres://notes:secret@db:5432/notes
  db:
    environment:
      POSTGRES_DB: notes           env_file: - .env was folded into environment
      POSTGRES_PASSWORD: secret
      POSTGRES_USER: notes

When the same key appears in both, environment: wins. Tested directly: with GREETING set in an env file and again under environment:, docker compose config reported GREETING: from the environment key, while a second key present only in the file came through untouched. Treat env_file: as your defaults and environment: as the override, and keep a .env holding real credentials out of version control.

Section 4 · When it runs

Why depends_on is not enough, and what fixes it

Part 1 mentioned that depends_on waits for the container to start, not for the software inside it to be ready. That sounds like a technicality until you watch it break a stack, so here it is breaking on your machine. The web service in this example checks the database once at start-up and exits if it cannot reach it.

With plain depends_on: - db, on a fresh volume

$ docker compose up -d
 Container notes-api-db-1   Started
 Container notes-api-web-1  Started     immediately after. Compose considers the job done.

$ docker compose ps -a
notes-api-db-1    db     Up 4 seconds
notes-api-web-1   web    Exited (1) 3 seconds ago

$ docker compose logs web
web-1  | checking the database before we start serving
web-1  | database unreachable: [Errno 111] Connection refused
web-1  | giving up

The database container was running the whole time. PostgreSQL simply had not finished starting: on a fresh volume it has to initialise its data directory before it will accept a connection. Compose did exactly what it promised, and the promise was not the one you needed.

The fix has two halves and both are required. Give db a healthcheck, so that there is a way to ask whether it is ready, then change depends_on to wait for that answer instead of for the container.

The same up, with the healthcheck in place

$ docker compose up -d
 Container notes-api-db-1   Started
 Container notes-api-db-1   Waiting          this line is the whole difference
 Container notes-api-db-1   Healthy
 Container notes-api-web-1  Started

real    0m6.181s

$ docker compose ps
notes-api-db-1    db     Up 5 seconds (healthy)
notes-api-web-1   web    Up 4 seconds

$ docker compose logs web
web-1  | checking the database before we start serving
web-1  | database is up, serving on port 8000

$ curl -s localhost:8080
Notes API v1
db: postgres://notes:secret@db:5432/notes

Note the two dollar signs in pg_isready -U $$POSTGRES_USER. A single $ would be substituted by Compose while it reads the file, on your machine, where that variable does not exist, and the check would run with an empty user. Doubling it leaves a literal $ in the command so the shell inside the container expands it instead, from the container’s own environment. This is the standard escape wherever a compose value must reach the container with its dollar signs intact.

And restart:, for what happens after start-up

ValueWhat the daemon does when the container stops
noNothing. The default, and the right choice for one-off tasks that are meant to finish.
on-failureRestarts only on a non-zero exit. Add :5 to cap the number of attempts.
alwaysRestarts whenever it stops, and starts it again when the daemon itself starts, even if you had stopped it deliberately.
unless-stoppedThe same, except that a container you stopped by hand stays stopped. The sensible default for a long-running service.

A restart policy is not a substitute for a healthcheck. It reacts to a container that has already died. A healthcheck lets Compose avoid the death in the first place, and for a service that hangs without exiting it is the only one of the two that notices anything is wrong.

Section 5 · The daily loop

The commands you will actually type

Nine commands cover almost everything. They all act on the project as a whole, and they all expect to be run from the folder holding the compose file.

Start everything

docker compose up -d

Creates whatever is missing and starts it. Safe to run repeatedly: it recreates only the services whose definition changed.

Start after a code change

docker compose up -d --build

The same, plus a rebuild of every service using build:. Required whenever the change is inside the image.

See what is running

docker compose ps

This project only. Shows status, health, and published ports. Add -a to include containers that have exited, which is where crashes hide.

Read the output

docker compose logs -f web

Follows the log as it is written. Drop the service name to interleave all of them, each line prefixed with the service it came from.

Run something inside

docker compose exec db psql -U notes

Runs a command in a service that is already up. Use the service name, not the container name. sh gets you a shell.

Check the file

docker compose config

Parses and prints the file with variables resolved. The fastest way to catch a YAML mistake or to see what a value became.

Restart one service

docker compose restart web

Stops and starts the existing container. It does not re-read the compose file, so use up -d after an edit.

Stop and clean up

docker compose down

Removes the containers and the network. Named volumes are deliberately kept, so your data comes back on the next up.

Delete the data as well

docker compose down -v

The same, plus every named volume in the project. Irreversible. Use it to start a database from empty, and never by reflex.

What down keeps, tested on a real row

$ docker compose exec db psql -U notes -d notes -c "INSERT INTO notes(body) VALUES ('survives down');"
INSERT 0 1

$ docker compose down
 Container notes-api-web-1  Removed
 Container notes-api-db-1   Removed
 Network notes-api_default  Removed
no mention of the volume

$ docker volume ls | grep pgdata
local     notes-api_pgdata

$ docker compose up -d
$ docker compose exec db psql -U notes -d notes -c 'SELECT * FROM notes;'
 id |     body
----+---------------
  1 | survives down
(1 row)

$ docker compose down -v
 Volume notes-api_pgdata Removed
$ docker volume ls | grep pgdata
(nothing)

Section 6 · Reference

Every key on this page, and what catches people out

KeyWhat it doesWhat catches people out
image:Uses a published image as it is.Pin a real version. :latest means different software on different machines.
build:Builds an image from a Dockerfile.The value is the build context folder, not the Dockerfile. A plain up will not rebuild it.
ports:Publishes a container port on your machine.Host on the left. Reversed, it fails as a dropped connection rather than an error.
volumes: (bind)Maps one of your folders into the container.It hides whatever the image had at that path, including files the build put there.
volumes: (named)Mounts storage that Docker manages.It must also appear in the top-level volumes: block, or Compose rejects the file.
environment:Sets variables inside the container.Beats env_file: for the same key. A value like 5432 arrives as a string.
env_file:Loads variables from a file into the container.Different from the .env beside your compose file, which Compose reads for ${...}.
depends_on:Sets start-up order.The short form waits only for the container to start. Almost never what you want before a database.
healthcheck:Tells the daemon how to test readiness.Escape variables as $$, or Compose substitutes them on your machine instead.
restart:What to do after the container stops.It reacts to a crash. It cannot prevent one, and it never notices a hung process.
name:Fixes the project name.Without it the folder name is used, so renaming the folder orphans your volumes.

One habit worth forming. Run docker compose config after every edit. It is instant, it catches indentation mistakes before they turn into confusing runtime errors, and it shows you the file as Compose sees it, which is not always the file you think you wrote.

Section 7 · Check yourself

Eight questions on Part 2

Same format as last time. Answer all eight, then check; the explanations appear in place, including for the ones you get right.

Question 1Your service says build: .. What does the dot refer to?

It names the build context, not a file. That folder is the root for every COPY in the Dockerfile, which is why COPY app/ . works and why a path outside the context cannot be copied at all. The Dockerfile is found there by default; dockerfile: points somewhere else when you need it.

Question 2Your web service uses build: and has no bind mount. You edit the source and run docker compose up -d. What happens?

An image with the right name already exists, so Compose uses it. Section 2 showed the image id unchanged across a plain up and changed after up --build. This is the usual explanation for “my change is not showing up”.

Question 3Your app listens on 8000 inside the container. You write ports: - "8000:8080". What do you see?

Host on the left, container on the right, and reversing it is not an error. The host side is published, so the connection is accepted; the container side points at a port with nothing behind it, so it dies immediately. docker compose ps gives it away by listing the real port as unpublished alongside the mapping.

Question 4Which entry also needs a line in the top-level volumes: block?

Only the named volume. A bare word on the left means storage Docker has to create, so it must be declared. A path starting with . or / is a folder that already exists on your machine, and needs no declaration.

Question 5You write depends_on: db: condition: service_healthy. What else must be true?

The condition is only as good as the check behind it. service_healthy reads a status the daemon produces by running the healthcheck command; with no healthcheck defined there is no status to wait for. The two halves always go in together.

Question 6Why is it pg_isready -U $$POSTGRES_USER, with two dollar signs?

It protects the variable from being substituted too early. A single $ would be resolved by Compose on your machine, where POSTGRES_USER is not set, and the check would run with an empty user. $$ leaves a literal $ for the container’s own shell.

Question 7A key is set in both env_file: and environment:. Which value reaches the container?

environment: wins. The useful pattern follows from that: keep shared defaults in the file and override the one or two that differ inline. Keys present only in the file still come through untouched.

Question 8You run docker compose down, then docker compose up -d. Is the data in your database still there?

The data survives, and Section 5 showed a row coming back after a full down. down -v is the command that deletes named volumes, and it is the one to be careful with. If data ever does disappear across a down, suspect a renamed folder: that changes the project name, and with it the volume being looked for.

That completes the track. You can now read a compose file a stranger wrote, and write one for a web and database stack without copying a template, which was the goal set at the start of Part 1.

Where to go from here, when a project needs it: profiles: for services that should not start every time, several -f files layered for development against production, deploy: and replicas, and a top-level networks: block for when one flat project network is no longer enough.
