DOCKER → SERVER → BROWSER

What happens when someone opens your app's URL?

Your containers run on a server. A domain helps the browser find it. An encrypted connection carries the request to a reverse proxy, which passes it to your app.

Let's follow https://myapp.com to a small task app with a web container, an API container, and a database. We'll use one server to keep the route visible.

Before the visit, your app needs a home

A server is a computer that runs your app and accepts network requests. Here, it is a rented Linux machine with a public IP address. It keeps running when your laptop is off.

Deployment means putting a version of your app on that machine and starting it with the settings it needs. A Docker image packages the app and its dependencies; a container is a running instance of that image.

On the server, you supply production configuration and secrets, keep database data in persistent storage, and make the proxy reachable through published ports and firewall rules. Starting containers alone does not give the app a public domain or HTTPS.

1. The browser finds the server's address

myapp.com is a domain name. DNS, the Domain Name System, lets the browser look up an IP address for that name. The lookup may already be cached.

For this setup, you configure the domain's DNS with an A record pointing to the server's public IPv4 address. An AAAA record does the equivalent job for IPv6.

myapp.com → DNS lookup → 203.0.113.10

The address above is a documentation example. DNS supplies the address; website requests then travel to the server. DNS does not choose between / and /api/tasks.

Reference: MDN on browsers, DNS, and HTTP.

2. The browser establishes HTTPS

Because the URL starts with https://, the browser connects securely, using port 443 by default. A port identifies the service to contact at an IP address.

HTTPS is HTTP protected by TLS, the protocol that encrypts traffic and detects tampering. During connection setup, the server presents a certificate. The browser checks that it is valid for myapp.com and trusted, then establishes encryption keys.

In our setup, the reverse proxy handles TLS. It decrypts requests and encrypts responses. The private connection from the proxy to an app container uses HTTP here; that connection needs its own TLS configuration if you want it encrypted too.

A proxy such as Caddy can obtain and renew certificates automatically when the domain and certificate validation are configured correctly. Nginx can also handle HTTPS, with certificates supplied through your chosen setup.

Reference: Caddy's automatic HTTPS documentation.

3. The proxy chooses a container

A reverse proxy receives requests on behalf of your app. It reads the requested hostname and path, then forwards the request to the service you configured. The browser keeps using your public URL.

Browser requestsProxy forwards toService returns
https://myapp.com/http://web:3000/The page
https://myapp.com/api/taskshttp://api:8000/api/tasksTask data as JSON

These are example routing rules, with the path preserved. Docker resolves web and api inside the shared network. Your visitor's browser cannot use those private service names.

References: Docker Compose networking and Caddy request forwarding.

4. The page loads, then asks for data

  1. The browser requests /. The proxy forwards it to the web container, which sends back HTML. The browser also requests the page's CSS and JavaScript.
  2. The downloaded JavaScript runs in the browser. Our task app calls fetch("/api/tasks"), which uses the same public site, https://myapp.com/api/tasks.
  3. The proxy sends that request to the API. The API reads tasks from the database and returns JSON through the proxy to the browser.
  4. The browser uses the JSON to display the task list. Your API code ran on the server; the code drawing this task list ran in the visitor's browser.
Why not call localhost:8000 from the frontend?

In browser JavaScript, localhost means the visitor's own computer. It would try to reach an API there. Use the public API URL, or a relative path such as /api/tasks when the proxy routes API requests on the same site.

Next time, deploy a new version

The server keeps running the version you deployed until you replace it. Editing code on your laptop does not update those running containers.

CI/CD automates checks and delivery. A typical pipeline tests a change, builds a new image, pushes it to the registry, and updates the server's containers. Continuous delivery can keep a human release step; continuous deployment makes that release automatic.

The visitor still uses https://myapp.com. If the server address and routing stay the same, DNS and the public URL can stay the same while the app behind them changes.

This example uses one server and a browser-rendered task app. Larger deployments can add load balancers or a CDN, but the same jobs still need doing: finding an address, securing the connection, routing requests, and returning responses.
