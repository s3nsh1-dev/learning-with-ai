Stages 2, 3 & 4 Technical Glossary

  • E2E — End-to-End Testing: Complete full-stack verification where an automated browser clicks real UI elements wired to live containers.
  • CI — Continuous Integration: The automated practice of running unit, integration, and E2E suites on every pull request before code merges.
  • CD — Continuous Delivery: The automated packaging and deployment of verified code to registry and staging or production servers.
  • PR — Pull Request: A proposed code change from a branch or fork waiting for automated verification and peer review before merge.
  • GHCR — GitHub Container Registry: GitHub's private OCI registry hosted at ghcr.io for storing and distributing versioned Docker images.
  • OCI — Open Container Initiative: Open industry standards for container image formats, layers, and registry distribution specifications.
  • SHA — Commit Hash (40-char): The cryptographic unique identifier of a specific Git commit; used for immutable container image tags.
  • GHA — GitHub Actions: GitHub's workflow automation runner system executing jobs inside isolated Linux virtual machines.
  • GITHUB_TOKEN — Automatic Scoped Token: A temporary credentials token generated per workflow run with granular, explicit permissions.
  • Buildx — Docker BuildKit CLI: Docker's advanced builder offering parallel multi-stage building, cross-platform compilation, and cache backends.
  • TCP — Transmission Control Protocol: The underlying networking protocol over which the test runner connects to PostgreSQL port 5432 or 5433.
  • FIFO — First-In, First-Out: Sequential ordering guarantee essential when processing database seed queues or teardown hooks.
  • UUID — Universally Unique Identifier: Random 128-bit labels used to isolate test records so parallel test workers never overwrite each other.
  • SQL — Structured Query Language: Database command language used for migrations, seed data, and table truncation during cleanup.
  • ORM — Object-Relational Mapping: Database abstraction layer (like Prisma or Drizzle) that handles schema migrations and test queries.
  • HTTP — Hypertext Transfer Protocol: Request-response protocol validated by assertion checks on status codes like 200, 201, 400, or 404.
  • EC2 — Elastic Compute Cloud: AWS virtual machines hosting production Docker containers.
  • SSH — Secure Shell: Encrypted protocol on TCP port 22 using public-key cryptography for host management.
  • SG — Security Group: Stateful host-level virtual firewall regulating inbound and outbound network traffic on EC2.
  • PAT — Personal Access Token: Scoped GitHub authentication token with read:packages permission used on EC2 to pull private images from GHCR.
  • YAML — YAML Ain't Markup Language: Configuration standard defining multi-container environments in compose.prod.yaml.

01 / Stage 4 · Continuous Delivery

Publishing to GHCR: Credentials & Least Privilege

Once Stage 3's verification jobs pass, we transition from Continuous Integration (testing) to Continuous Delivery (publishing release artifacts). We publish our private client and server images to GitHub Container Registry (GHCR) at ghcr.io.

In legacy setups, developers frequently created long-lived Personal Access Tokens (PATs) and pasted them into repository secrets. This is an enormous security liability: if leaked, a PAT grants access to everything the developer owns. In modern GitHub Actions, we use the automatic, ephemeral GITHUB_TOKEN with granular, explicit permissions.

The Principle of Least Privilege in CI/CD

By default, we set top-level permissions: {}. In the publishing job, we grant only the two exact permissions required to pull the Git commit and publish container packages:

Permission Scope Granted Level Technical Rationale
contents read Allows checking out the merged commit code to build the Dockerfile
packages write Authorizes pushing image layers and manifests to ghcr.io
id-token, deployments, etc. none Eliminates unnecessary privilege attack vectors

The Release Boundary Condition

The publishing job must declare two guardrails: it must wait for all test jobs to succeed (needs: [...]), and it must execute only when code is merged into the trusted main branch:

.github/workflows/ci-cd.yml (GHCR Authentication & Guardrails) 
  publish-images:
    name: Build & Publish GHCR Images
    runs-on: ubuntu-latest
    needs: [test-client, test-server, test-e2e]
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    permissions:
      contents: read
      packages: write
    steps:
      - name: Checkout Merged Code
        uses: actions/checkout@v4

      - name: Log in to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
💡 Why needs: [...] is Critical

If you omit needs: [test-client, test-server, test-e2e], GitHub Actions will run the publish-images job in parallel with your tests! Broken code could be packaged and pushed to the registry before the test failure even registers.

02 / Stage 4 · Build Engineering

Docker Buildx Layer Caching & OCI Metadata

Building a Docker image from scratch inside CI is slow. If a developer only changed one line of CSS in the client, why should the runner re-download the Node base image and re-execute pnpm install?

With Docker Buildx and BuildKit, GitHub Actions can cache intermediate Dockerfile build layers directly inside GitHub's caching backend using type=gha. Subsequent runs reuse unchanged layers, reducing image build times from 3 minutes to 15 seconds.

Standard OCI Labels & Traceability

Every container image published to production should be self-documenting. Using docker/metadata-action, we extract Git metadata and embed standard OCI (Open Container Initiative) annotations:

  • org.opencontainers.image.source: Links the image directly back to the GitHub repo URL.
  • org.opencontainers.image.revision: Contains the exact 40-character Git commit SHA.
  • org.opencontainers.image.created: Timestamp of the build.
.github/workflows/ci-cd.yml (Buildx Layer Caching & Metadata) 
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Extract OCI Metadata for Client
        id: meta-client
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}-client
          tags: |
            type=sha,prefix=sha-,format=short
            type=raw,value=latest,enable=${{ github.ref == 'refs/heads/main' }}

      - name: Build and Push Client Image
        uses: docker/build-push-action@v5
        with:
          context: ./client
          push: true
          tags: ${{ steps.meta-client.outputs.tags }}
          labels: ${{ steps.meta-client.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
💡 What mode=max Does

Standard Docker caching only saves the final exported image layer. Specifying cache-to: type=gha,mode=max instructs BuildKit to cache layers from intermediate multi-stage build stages (such as the pnpm compilation container), maximizing cache hits on future commits.

03 / Stage 4 · Production Rigor

Immutable Commit SHA Tags & Pipeline Review

The single most dangerous anti-pattern in container deployment is deploying :latest. In this final topic, we establish why immutable commit SHA tags are essential, and review the complete, unified delivery pipeline.

The "Latest" Trap vs Immutable Releases

When you tag a Docker image as latest, you are creating a mutable, moving target:

Dimension The :latest Anti-Pattern Immutable SHA Tag (:sha-e8f91c0)
Determinism Ambiguous. Which Git commit does this container run? Nobody knows without running inspection commands. Cryptographically absolute. The tag matches the exact Git commit SHA in the repository history.
Rollback Safety Impossible. Rolling back means re-tagging or guessing which version was previously deployed. Instant. Changing one environment variable (IMAGE_TAG=sha-a1b2c3d) rolls back cleanly.
Docker Daemon Caching Host may skip pulling if a local image tagged latest already exists on disk. Every commit is a brand-new unique tag. docker compose pull always retrieves the exact release.

04 / Stage 5 · Deployment Architecture

Dev vs. Prod Compose: The EC2 Build Boundary

In local development, Docker Compose is optimized for developer ergonomics: hot reloading, mounting local directories, and building images on the fly with build: .. In production, using that same Compose file on EC2 is a severe operational hazard that causes server crashes, build non-determinism, and security vulnerabilities.

The Golden Rule: Never Build on Production EC2

A production virtual machine is a runtime host, not a build machine. When an EC2 instance attempts to build Docker images directly from source, three critical failure modes occur:

  • Host Memory Exhaustion (OOM Spikes): Running npm run build or compiling TypeScript requires heavy CPU and hundreds of megabytes of RAM. On common EC2 instances (such as t2.micro or t3.micro with 1 GB RAM), build spikes trigger the Linux kernel Out-Of-Memory (OOM) killer, which abruptly terminates running production processes like PostgreSQL or Nginx.
  • Toolchain Sprawl & Attack Surface: Building on the server requires storing full Git source code repositories, Git credentials, Node.js runtimes, compilers, and development dependencies on the live production machine. If the server is probed or compromised, attackers gain instant access to your source code and build tools.
  • Destruction of CI Guarantees: CI pipelines exist to build, test, and vet an exact, immutable artifact. Building from source on EC2 means you are deploying an untested artifact whose installed packages may subtly differ from what was verified in CI.
⚠️ The Architectural Separation

CI Job (GitHub Actions): Builds images, runs test suites, scans for vulnerabilities, tags with the commit SHA, and pushes to GHCR.
Production Host (EC2): Pulls the prebuilt image from GHCR and starts the container. It never runs docker build or compiles source code.

Architectural Contrast: Development vs. Production Compose

🛠️ Development (compose.yaml)
  • Image Source: build: ./client
  • Source Bind Mounts: - ./client:/app (enables instant hot reloading)
  • Port Exposure: Binds host ports for all services (5432:5432, 3000:3000) for easy debugging
  • Restart Policy: no (default)
  • Environment: Plain text defaults inside file
🚀 Production (compose.prod.yaml)
  • Image Source: image: ghcr.io/${GH_OWNER}/todo-client:${IMAGE_TAG}
  • Source Bind Mounts: STRICTLY ZERO (code baked immutably inside image)
  • Port Exposure: Only Nginx (80:80) exposed to host; API & DB remain private
  • Restart Policy: restart: unless-stopped
  • Environment: Loaded dynamically from host .env file (chmod 600)
compose.prod.yaml (Service Definition Pattern) 
services:
  api:
    image: ghcr.io/${GH_OWNER}/todo-api:${IMAGE_TAG}
    restart: unless-stopped
    expose:
      - "3000" # Internal to Docker bridge network only; NO host port binding
    environment:
      - DATABASE_URL=postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}?schema=public
      - PORT=3000
    depends_on:
      db:
        condition: service_healthy
    networks:
      - todo-net
05 / Stage 5 · Network Topology

Production Compose Architecture & Private Network Isolation

A secure production deployment strictly minimizes the public network attack surface. External web traffic must enter through a single hardened reverse proxy gateway (Nginx on port 80), while the backend API and database communicate exclusively over an isolated, internal Docker bridge network.

The Three-Tier Production Topology

In our production Compose architecture, three services operate under the principle of least network privilege:

  1. Nginx Reverse Proxy (Gateway): The only container with a public host port binding (ports: ["80:80"]). It terminates incoming HTTP connections, serves pre-rendered static frontend assets directly, and proxies /api/* requests internally to the backend.
  2. Express API (Application Server): Binds no public host ports. It declares expose: ["3000"], making port 3000 accessible only to sibling containers sharing the todo-net bridge network.
  3. PostgreSQL 16 (Database): Completely inaccessible from outside the Docker host. It communicates strictly with the Express API container over db:5432 and persists data using a dedicated named Docker volume (db_data).

Interactive Topology: Production Network Isolation

Architecture View: Full Topology — Port 80 is the sole ingress on the EC2 host. Express and PostgreSQL communicate over the private todo-net bridge with no public exposure.

The Complete compose.prod.yaml Specification

Here is the canonical, verified production Compose contract used for our deployment:

compose.prod.yaml 
services:
  nginx:
    image: ghcr.io/${GH_OWNER}/todo-client:${IMAGE_TAG}
    restart: unless-stopped
    ports:
      - "80:80"
    depends_on:
      - api
    networks:
      - todo-net

  api:
    image: ghcr.io/${GH_OWNER}/todo-api:${IMAGE_TAG}
    restart: unless-stopped
    expose:
      - "3000"
    environment:
      - NODE_ENV=production
      - PORT=3000
      - DATABASE_URL=postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}?schema=public
      - JWT_SECRET=${JWT_SECRET}
    depends_on:
      db:
        condition: service_healthy
    networks:
      - todo-net

  db:
    image: postgres:16-alpine
    restart: unless-stopped
    expose:
      - "5432"
    environment:
      - POSTGRES_USER=${POSTGRES_USER}
      - POSTGRES_PASSWORD=${POSTGRES_PASSWORD}
      - POSTGRES_DB=${POSTGRES_DB}
    volumes:
      - db_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 5
    networks:
      - todo-net

volumes:
  db_data:

networks:
  todo-net:
    driver: bridge
06 / Stage 5 · Configuration & Dry Run

Decoupling Release Tags from Runtime Secrets & Dry Run Verification

A robust deployment contract cleanly separates release parameters (which Git commit SHA image tag is deploying) from runtime secrets (database passwords and JWT tokens). Conflating the two leads to credentials leaking into Git history or deployment scripts breaking across releases.

The Separation of Concerns

📦 Release Parameters (Dynamic)

GH_OWNER, IMAGE_TAG (e.g. sha-e8f91c0)
Supplied by the deployment pipeline during CD. These change on every single deployment, are safe to log publicly, and identify the exact immutable code version.

🔒 Runtime Secrets (Static & Sensitive)

POSTGRES_PASSWORD, JWT_SECRET, DATABASE_URL
Stored strictly in an uncommitted .env file on the EC2 host. Owned by the system administrator, chmod 600, and never checked into GitHub.

How Compose Resolves Environment Variables

When compose.prod.yaml contains ${IMAGE_TAG}, Docker Compose interpolates the value in this exact order of precedence:

  1. Shell Ambient Variables: Values exported in the current terminal session (e.g. export IMAGE_TAG=sha-e8f91c0).
  2. The .env File: Key-value pairs in the adjacent .env file in the Compose directory.
  3. Default Fallbacks: In-line syntax like ${IMAGE_TAG:-latest} if specified.
Sample /opt/todo-app/.env (Secured on EC2 Host) 
# Deployment parameters (or passed via CD environment)
GH_OWNER=octocat
IMAGE_TAG=sha-e8f91c0

# Production database credentials (Never commit to Git!)
POSTGRES_USER=todo_prod_user
POSTGRES_PASSWORD=super_secret_db_password_98234
POSTGRES_DB=todo_prod

# Application secrets
JWT_SECRET=production_jwt_signing_key_4a9b2c8f1e7d

The Golden Pre-Flight Check: docker compose config

Never deploy blindly. Before pulling images or running up -d, execute:

EC2 Terminal (Dry-Run Validation) 
docker compose -f compose.prod.yaml config

This command acts as a comprehensive dry-run parser:

  • Validates YAML indentation, syntax, and schema correctness.
  • Resolves and prints all ${VARIABLE} substitutions in plain text.
  • Warns immediately if any referenced environment variable is missing or empty.
  • Validates volume bindings, network bridges, and port declarations without launching any containers.
💡 CI/CD Sanity Check

You can run docker compose -f compose.prod.yaml config --quiet inside your GitHub Actions pipeline before deploying to guarantee that changes to your Compose file never introduce syntax errors onto the live host!

07 / Stage 6 · Network Perimeter

EC2 Network Perimeter: Security Groups & SSH Key Hardening

Before provisioning software on an AWS EC2 instance, you must configure its perimeter defenses. AWS Security Groups act as a virtual firewall controlling inbound and outbound network traffic at the hypervisor level, long before packets even reach the Linux operating system.

The Principle of Least Network Privilege

A common beginner mistake is opening all ports (0.0.0.0/0 on ports 0–65535) or exposing port 5432 to connect remote GUI clients. In production, this invites automated bots to brute-force database credentials within minutes.

Rule Type Protocol & Port Source CIDR Rationale
Inbound TCP 80 (HTTP) 0.0.0.0/0 Public access for web visitors hitting Nginx.
Inbound TCP 443 (HTTPS) 0.0.0.0/0 Encrypted TLS web traffic.
Inbound TCP 22 (SSH) YOUR_IP/32 or Bastion Administrative host access; never open to the public internet.
Inbound TCP 5432, 3000 NONE (BLOCKED) Express and PostgreSQL live exclusively on the private Docker bridge network.
Outbound All Traffic 0.0.0.0/0 Allows the host to fetch Ubuntu security updates and pull images from GHCR.

Interactive Firewall: AWS Security Group Filtering

Security Group View: Active Rules — HTTP (80) is open to 0.0.0.0/0. SSH (22) is restricted to the admin IP. Direct database probes on 5432 are silently dropped at the hypervisor.

SSH Key Pair Hardening: Why chmod 400 is Mandatory

When AWS generates your private key (e.g. todo-deploy-key.pem), your local operating system may default file permissions to 0644 (readable by other users on your workstation).

OpenSSH clients strictly enforce private key security. If you attempt to connect with loose permissions:

OpenSSH Terminal Warning 
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@         WARNING: UNPROTECTED PRIVATE KEY FILE!          @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@

It is required that your private key files are NOT accessible by others.

Fix the permissions immediately before connecting:

Workstation Terminal

ssh -i ~/.ssh/todo-deploy-key.pem ubuntu@<EC2-PUBLIC-IP>
08 / Stage 6 · Host Provisioning

Docker Engine Provisioning & Least-Privilege GHCR Access

With network perimeters in place, we provision modern container runtime tooling on Ubuntu 24.04 LTS. Using official upstream Docker repositories ensures access to Docker Engine v26+ and the integrated docker compose v2 plugin, avoiding broken legacy packages.

Why Never Install docker.io

Running sudo apt install docker.io installs Ubuntu's frozen upstream snapshot. These packages are frequently months behind, miss CVE security patches, and do not bundle the official Compose v2 plugin (leaving you stuck with deprecated Python-based docker-compose v1).

Production Setup: Official Docker Apt Repository

EC2 Host Terminal (Ubuntu 24.04 LTS) 
# 1. Update system package index and install prerequisites
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg

# 2. Add Docker's official GPG key
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# 3. Add official Docker repository to Apt sources
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# 4. Install Docker Engine and the Compose plugin
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Granting Non-Root User Permissions

By default, the Docker daemon socket (/var/run/docker.sock) is owned by root:docker. If regular users run docker ps, they receive permission denied while trying to connect to the Docker daemon socket.

To allow the non-root ubuntu user and future CI automation scripts to manage containers without needing passwordless root sudo:

EC2 Host Terminal 
# Add the ubuntu user to the docker group
sudo usermod -aG docker ubuntu

# Activate the group changes in the current shell session
newgrp docker

# Verify non-root execution
docker run --rm hello-world

Authenticating with GHCR: The Principle of Least Privilege

The EC2 instance needs to pull container images from GitHub Container Registry. Never log in with your primary GitHub account password or a Personal Access Token with broad repo write scopes.

⚠️ Least-Privilege PAT Scope

Create a dedicated GitHub Personal Access Token (classic or fine-grained) scoped strictly to read:packages. If the EC2 host is ever compromised, the attacker cannot read private source code repositories, push malicious images, or alter account settings.

Secure Login via --password-stdin

Avoid passing tokens via the command-line flag -p $TOKEN:

EC2 Host Terminal (Secure GHCR Login) 
# Secure authentication without exposing token in process tables or history
echo "$GHCR_PAT" | docker login ghcr.io -u <GITHUB_USERNAME> --password-stdin

Why --password-stdin is mandatory: CLI arguments are visible to any local user running ps aux, stored in /proc/<pid>/cmdline, and saved in plain text in ~/.bash_history. Piping via standard input prevents credential leakage entirely.

Host Smoke Testing & End-to-End Health Verification

Before handing deployment responsibilities over to automated GitHub Actions CD pipelines, we perform a manual deployment and comprehensive smoke test. This proves that all infrastructure layers—Security Groups, Docker daemon, GHCR authentication, Compose networking, and database persistence—function cohesively.

The Four-Tier Smoke Test Verification Plan

Follow this step-by-step verification checklist to prove production readiness:

Step 1: Test Image Pull from GHCR

Confirm that the host can pull private container images using the least-privilege PAT credentials:

🔍 Troubleshooting: The Classic Ingress Timeout

Symptom: curl http://localhost/api/health succeeds inside the EC2 terminal, but accessing http://<EC2-PUBLIC-IP> from your browser hangs indefinitely and times out.
Diagnosis: Your containers are healthy and Nginx is listening. The timeout indicates packets are being silently dropped by AWS before reaching the EC2 virtual network interface.
Fix: Open AWS EC2 Console → Security Groups → Edit Inbound Rules → Add Type: HTTP (TCP 80), Source: 0.0.0.0/0.
