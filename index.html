Field notes / Docker networking

Docker networking, one topic at a time

Read one topic, mark it complete, and come back whenever you like.

One EC2 machine. Several different “here”s.

Your VPS knowledge still applies. EC2 is the server. Docker runs your web server, API, and database in separate containers on that server. Each container has its own localhost.

The question that makes an address click is “Where is the code making this request running?” A browser and a web container are two different callers.

Follow one request for a list of todos

We’ll use one public entry point. The web container serves the frontend and forwards /api/ requests to the API container. The API queries PostgreSQL. A server that forwards requests this way is a reverse proxy.

The frontend has two locations.

The web container sends HTML and JavaScript files to your browser. That JavaScript then runs on your laptop. Its fetch('/api/todos') calls the same public origin that served the page. The web server receives it and makes a separate internal request to http://api:8000/todos.

“The API only receives web requests” can mean that outside clients cannot connect directly to port 8000. This setup achieves that. People can still call the public /api/todos route themselves, without your UI. The API must still authenticate users and check permissions. Private networking does not prove that a request came from your frontend code.

api is a private name, not a special URL

In http://api:8000, http is the protocol, api is the destination name, and 8000 is the destination container’s listening port. Docker’s internal name lookup translates the Compose service name api into its container IP for containers sharing its network. Docker’s networking guide

http://web:3000 works the same way. Another container sharing web’s network can use it to reach web. Your browser normally uses http://EC2_PUBLIC_IP, not http://web:3000. These private names work on a VPS too; they are a Docker feature, not an AWS feature.

Why localhost used to work

If your frontend and backend ran directly on your laptop, the browser could call localhost:8000 on that same laptop. With ordinary Docker bridge networking, web’s localhost:8000 points back into web, where no API is listening. Use api:8000 to cross into the API container.

Listening ports and published ports

Address or settingWhat it means here
0.0.0.0:8000API listens on all its container’s IPv4 interfaces. This is a bind address, not the URL callers should use.
"80:3000"Publish EC2 host port 80 to web container port 3000. Inside Docker, web is still reached on 3000.
EXPOSE 8000Image metadata describing an intended port. It does not publish that port or start a listener.
expose: [8000]Optional Compose documentation of an internal port. Shared-network containers can connect without it. It is not an access-control rule.
db:5432A PostgreSQL connection destination. Your database driver uses the PostgreSQL protocol, not HTTP.

Published ports connect host ports to container ports. Compose’s service reference explains ports, expose, and network membership.

Put this on an EC2 instance

This walkthrough assumes a fresh Ubuntu 24.04 EC2 instance and prebuilt Linux images for your app. It is a networking setup with an initial HTTP check. Add HTTPS before using real logins or private data.

1 / Prepare the Linux machine

Launch an Ubuntu 24.04 instance in a public subnet with an internet-gateway route and a public IPv4 address. Choose an instance architecture supported by your images. Attach storage large enough for images and database data.

In its security group, allow TCP 22 from your current IP for SSH and TCP 80 from your current IP for this first check. For a public website, web traffic will later need public access on 443. Do not add inbound rules for 3000, 8000, or 5432. A security group is AWS’s network firewall around the instance.

On your laptop
chmod 400 your-key.pem
ssh -i your-key.pem ubuntu@EC2_PUBLIC_IP

On EC2, install Docker Engine and the Compose plugin using Docker’s Ubuntu apt-repository instructions. Use the repository setup commands there, then install and check:

Inside the EC2 SSH terminal
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker run hello-world
sudo docker compose version
mkdir -p ~/todo-stack
cd ~/todo-stack

Know what your images need to do

An image is the packaged filesystem and startup instructions for a program. A container is a running instance of that image. Pulling an image downloads it; starting a container runs its program. Image names such as ghcr.io/YOUR_ORG/todo-api:1.0.0 identify packages in a registry. Service names such as api identify running services in this Compose project.

The two app image names below are placeholders. Replace them with images you or your team have built and pushed. A random frontend image will not automatically provide proxying, and a random API will not automatically understand these environment variables.

Web image contract

Serves built frontend files and listens on 0.0.0.0:3000. In this example it contains Nginx with the configuration below and files in /usr/share/nginx/html. Browser code uses fetch('/api/todos').

API image contract

Listens on 0.0.0.0:8000, implements GET /todos, and reads DATABASE_URL. It uses a PostgreSQL driver, creates its schema through your migration process, and retries transient database connections.

Inside your web image · /etc/nginx/conf.d/default.conf
server {
    listen 3000;
    root /usr/share/nginx/html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://api:8000/;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

The trailing slash in proxy_pass makes /api/todos become /todos upstream. If your API expects /api/todos, use proxy_pass http://api:8000; instead. This routing is web-server behavior that you configure, not something Docker adds. Nginx proxy_pass reference

Describe the containers and connections

Create compose.yaml in ~/todo-stack on EC2. Web and API share web_api. API and database share api_db. Web has no direct network connection to the database.

~/todo-stack/compose.yaml
services:
  web:
    image: ghcr.io/YOUR_ORG/todo-web:1.0.0
    ports:
      - "80:3000"
    networks: [web_api]
    depends_on: [api]
    restart: unless-stopped

  api:
    image: ghcr.io/YOUR_ORG/todo-api:1.0.0
    environment:
      DATABASE_URL: "postgresql://todo:${DB_PASSWORD:?Set DB_PASSWORD}@db:5432/todo"
    networks: [web_api, api_db]
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:17
    environment:
      POSTGRES_USER: todo
      POSTGRES_PASSWORD: "${DB_PASSWORD:?Set DB_PASSWORD}"
      POSTGRES_DB: todo
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks: [api_db]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U todo -d todo"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped

networks:
  web_api:
  api_db:
    internal: true

volumes:
  pgdata:

The database network has no external gateway. The API also joins web_api, so the API can still make outbound requests if needed. Network membership permits communication in both directions; it does not enforce “only web may send HTTP.” Host administrators can also reach containers.

The named volume pgdata keeps database files when a database container is replaced. It does not protect you against losing the EC2 disk and is not a backup. PostgreSQL’s initialization variables apply when the data directory is empty; changing the password in this file later does not reset an existing database password. Official PostgreSQL image instructions

Set a password and start the containers

Create a local .env file next to Compose. This command generates a hex password, so it is safe to place in this example’s database URL without URL encoding. Keep this file out of Git.

On EC2 · in ~/todo-stack
umask 077
printf 'DB_PASSWORD=%s
' "$(openssl rand -hex 32)" > .env

# If your images are private, authenticate to their registry first:
sudo docker login ghcr.io

# Download web, API, and PostgreSQL images:
sudo docker compose pull

# Create networks, volume, and running containers:
sudo docker compose up -d
sudo docker compose ps

Run password generation once. For real production secrets, use your secret-management process; Docker administrators can inspect container environment variables. Before expecting /todos to work, run the schema migration command provided by your API project. There is no universal Docker command that creates your application’s tables.

depends_on waits for the database health check here. Web only waits for the API container to start, so initial requests may return 502 until the API is listening. Applications still need retries when dependencies restart. With this simple Nginx configuration, restart web after replacing API so Nginx resolves its current container address.

Check each hop from the right place

Use your actual public IP in the browser. The example commands below run in the EC2 SSH terminal unless stated otherwise.

First check the running services
sudo docker compose ps
sudo docker compose logs --tail=50 web api db
curl -i http://localhost/
curl -i http://localhost/api/todos

These two localhost requests start on the EC2 host. Host port 80 is published to web, so they can work. In your laptop’s browser, open http://EC2_PUBLIC_IP and inspect the Network tab. The API request should go to that same public host at /api/todos.

Test inside web · assumes the image contains wget
sudo docker compose exec web wget -qO- http://api:8000/todos

This request starts inside web, where Docker can resolve api. If the image lacks a diagnostic command, that alone does not mean networking failed. Check the API logs or use a tool your image actually includes.

Check PostgreSQL itself
sudo docker compose exec db psql -U todo -d todo -c 'SELECT 1;'
# Then inspect the API logs after requesting /api/todos:
sudo docker compose logs --tail=50 api

SELECT 1 inside db checks the database process. A successful app request that reads its table also verifies API-to-database connectivity, credentials, and schema.

Take the working connection to production

Attach a domain to a stable public address, configure a certificate and TLS termination on web or a load balancer, and allow 443 in the security group. Redirect HTTP to HTTPS. The internal destination can remain http://api:8000 on this single-host Docker network.

The example’s POSTGRES_USER creates an administrative database role. Give the production API a separate role limited to the tables and operations it needs. Use tested image versions or digests, database backups with restore checks, application authentication, and logs you can monitor. This single EC2 host is a single point of failure. If you later move the database to RDS, replace db:5432 with the RDS endpoint and configure its network access and TLS. It will no longer be a Compose service name.

Keep these three destinations separate.

Browser → public domain.
Web container → http://api:8000.
API container → db:5432 through a database driver.

Closer look / the actual network boundaries

Follow the address, then the connection

All three containers run on EC2. Each has a separate network environment, called a network namespace. Docker creates virtual network connections between them. There is no parent container.

Publishing and connecting are different operations. The browser uses a published host port to enter web. Web already has a network path to API, so it connects to API's own IP and listening port. How web finds the API

Why localhost stays inside its caller

localhost resolves to a loopback address, usually 127.0.0.1 or ::1. Linux keeps that traffic within the caller's own network namespace. It never reaches either bridge.

Request made inside web
localhost:8000
      ↓
web's own loopback
      ↓
port 8000 inside web

No API is listening there in this setup. The request fails inside web.

Request made in EC2's SSH terminal
localhost:8000
      ↓
EC2 host's own loopback
      ↓
port 8000 on the host

This can reach a server you started directly on EC2, if it listens there.

The repeated name localhost does not identify a shared place. Where the calling process runs decides which loopback it uses. Likewise, browser JavaScript uses your laptop's network environment, even when web served its files.
