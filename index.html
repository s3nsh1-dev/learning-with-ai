Before you start

Where the eight questions live

This is the file you finished in Stage 2. Each question stands on a real line of it.

01

Reference and declaration

You delete the last two lines. What happens on the next up -d?

services:
  db:
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:          <- these two
  pgdata:

The two lines say different things. The one under db says mount this. The top-level block says this exists. Compose will not invent the second from the first, and that refusal is a feature: a typo in the mount path turns into an error on startup instead of a database quietly writing into an empty anonymous volume you never find again.

02

Port order

.env sets WEB_PORT=3000. The service line is - "${WEB_PORT}:8000", and the app inside the container listens on 8000. Which address opens it?

Left is your side, right is inside. You type the left number into the browser; the right one has to match whatever the app actually binds to. Get them backwards and "8000:3000" is still a valid file that starts without a word of complaint. It just forwards to a port nothing is listening on, and you get an empty reply instead of an error.

03

Publishing versus reaching

db has no ports: line at all, yet web talks to it on 5432 all day. What is actually going on?

EXPOSE in a Dockerfile is a comment with syntax highlighting. It publishes nothing. The only thing ports: does is punch a hole from the host into the container, which is exactly what a database on your laptop does not need. Adding "5432:5432" out of habit puts Postgres in front of anything that can see your machine, on a coffee shop network included. If you want a GUI client on it, bind it to yourself: "127.0.0.1:5432:5432".

04

What depends_on does not wait for

A colleague's web dies on a cold laptop with [Errno 111] Connection refused. Their file already has depends_on: [db]. What actually fixes it?

Two halves, and neither works alone. The healthcheck is what gives db a state other than "running"; the condition is what makes web read that state before it starts. Ask for service_healthy against a service with no healthcheck and Compose rejects the file, because there is nothing to poll.

Answer A is the one worth arguing about. It does eventually get you a working stack, and plenty of production apps retry their own database connection on purpose. But on its own it turns a startup ordering bug into a crash loop you have to read the logs to notice, and it makes every cold start slower by the length of the restart backoff. Retrying is a fine belt. It is not the braces.

05

When a rebuild happens

You added httpx to requirements.txt and ran docker compose up -d. web still dies with ModuleNotFoundError: No module named 'httpx'. Why?

This is the quietest failure in the whole stage. There is no warning, no rebuild notice, no line in the output saying it skipped anything. up builds an image only when one does not exist yet; after that it is your job to ask. --build is the ask. Once you have been bitten twice you start typing it by reflex, which is fine.

06

How far down reaches

db keeps its rows in the named volume pgdata; web has the bind mount ./app:/app. Which command deletes the rows, and what happens to ./app?

Draw the line by ownership rather than by command. Docker made the containers, the network and the named volume, so Docker can remove all three; ./app is a folder you made, and no Compose flag reaches across into your filesystem. stop touches nothing but the running processes, down removes the containers and the network, and -v is the four keystrokes that add the volume to that list.

07

Which settings get inside

.env sits beside compose.yaml and contains TAG=16. You run docker compose exec web env | grep TAG. What comes back?

.env is read before any container exists. Compose uses it to fill in ${…} blanks in the text of the file, and then it is finished: it can set an image tag or a published port, and it can never set a variable your application reads. For that you want environment: for values you do not mind having in git, or env_file: for the ones that stay out of it. Two filenames one character apart, doing unrelated jobs.

08

A policy that overrules you

web has restart: unless-stopped. db has restart: always. You run docker compose stop, shut the laptop down, and boot it again in the morning. What is running?

The two policies behave identically on a crash and identically on a plain reboot, which is exactly why people mix them up. They part company on one event: a container you stopped deliberately. unless-stopped remembers that you stopped it. always does not, and starts it again as soon as the Docker daemon comes back. Pick unless-stopped and a stop stays a stop.
