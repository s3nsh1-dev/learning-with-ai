Map the Todo App Delivery System

Before writing a single GitHub Actions line or launching an EC2 instance, you must trace how this specific Todo app travels from a local feature branch to a live container stack.

01 / System Map · The Eight Stations

The Complete Delivery Highway: From Branch to Container

Continuous Integration (CI) and Continuous Deployment (CD) are not abstract automation scripts. For our Todo application, they form a strict, one-way assembly line that packages source code into immutable containers and lands them safely on AWS EC2.

In your local development environment, you edit files directly in client/ and server/, running Vite or tsx with source mounts. In production, source code is never shipped or compiled on the host. Instead, pre-built OCI container images are produced in the cloud, sealed with immutable version tags, and pulled onto the host server as ready-to-run black boxes.

The Eight Stations Broken Down

Each station along this rail performs one isolated responsibility:

  1. Feature Branch: Where code begins. Developers work on localized branches. Changes trigger checks but have zero authority over production.
  2. PR CI Gates: Automated test runner that executes quality linters, frontend builds, and backend integration tests against a disposable PostgreSQL container.
  3. Trusted Main Branch: The single release truth. Only code reviewed and merged into main can ever initiate package publication or deployment.
  4. GitHub Container Registry (GHCR): Hosts private, versioned container images. Every build is tagged with the exact immutable Git commit SHA.
  5. EC2 Compose Coordinator: A single directory on the server (/opt/todo-app) containing the production Compose contract and release pointers.
  6. Nginx Client Gateway: The sole container exposing a public port (port 80). It serves optimized React static assets and intercepts /api/* requests.
  7. Express API Server: The application backend. It runs purely on the internal Docker bridge network without any host port mapping.
  8. Neon PostgreSQL: Managed cloud database. Accessible only over TLS by the Express backend using credentials provisioned directly on the EC2 host.
Architecture Takeaway

The client and server are published as two distinct images because they have fundamentally different runtimes: the client is a static Nginx web server, while the backend is a persistent Node/Express API process connected to Neon.

02 / Workflow Boundaries · The Release Gate

Two Strict Lanes: Untrusted PRs vs. Trusted Main Releases

A catastrophic mistake in naive CI/CD setups is treating every Git push alike. In a production-grade system, pull requests and main pushes run on entirely separate security tracks.

Anyone with repository access (or fork access in open-source projects) can create a pull request with arbitrary code. If PR workflows possessed deployment credentials or registry publishing rights, an unreviewed PR could deploy broken code, overwrite official container images, or exfiltrate private database credentials.

Dimension Lane 1: Pull Request Gate (Untrusted) Lane 2: Main Push Pipeline (Trusted)
Trigger pull_request: [opened, synchronize] push: branches: [main]
Secrets Access None. Deployment secrets are withheld. Full access to EC2_SSH_PRIVATE_KEY, etc.
GITHUB_TOKEN Default read-only permissions. Explicitly granted packages: write.
Database Used Disposable, ephemeral PostgreSQL container. Disposable for tests; EC2 runs against Neon.
Artifact Output Test reports & lint logs only. Nothing published. Two immutable images pushed to GHCR with commit SHA.
EC2 Impact Zero. PRs never touch the network or EC2. SSH deploy triggered; containers refreshed.

Why We Reject the :latest Tag in Favor of Immutable SHAs

Many tutorials tag images with :latest. In professional software delivery, the :latest tag is an anti-pattern for three critical reasons:

  • Loss of Provenance: If a container on EC2 crashes, checking todo-server:latest tells you nothing about which Git commit caused the failure. An immutable SHA tag (e.g. ghcr.io/.../server:9f8a32b) points unambiguously to one exact line of Git history.
  • Docker Daemon Cache Pitfalls: The Docker daemon caches images. If your server already has an image labeled :latest, running docker compose up -d may silently skip pulling newer layers unless forced with explicit pull flags.
  • Impossible Rollback: When a deployment breaks, how do you roll back a :latest tag? You cannot tell Docker to "use the previous latest". With immutable commit SHAs, rolling back is as trivial as updating IMAGE_TAG to the previous SHA!
Proposed GitHub Actions Trigger Shape · delivery.yml 
name: Delivery Pipeline

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  # Check gates run for BOTH PRs and main
  test-and-lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # ... runs client lint, server integration tests with ephemeral Postgres ...

  # Publishing runs ONLY after tests pass AND only on main
  publish-images:
    needs: test-and-lint
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    permissions:
      contents: read
      packages: write
    # ... builds and pushes client & server images tagged with github.sha ...
The Principle of Least Privilege

By scoping packages: write strictly to the publishing job on main, pull requests are mathematically incapable of modifying your registry packages, even if someone attempts a malicious workflow modification.

Why the Express API Has No Public Host Port

Inspect the production Compose contract: Nginx maps 80:80, but Express uses expose: ["5000"] (or no port publishing at all). Why?

When a port is mapped with ports: ["5000:5000"], Docker binds that port to the host's network interfaces. Anyone who knows your EC2 public IP can send requests directly to Express, bypassing Nginx entirely.

By keeping Express on the internal Docker bridge network:

  • Direct Scanning is Blocked: Automated scanners on the internet only see port 80. Port 5000 does not exist to the outside world.
  • Single Ingress Policy: Nginx serves static client assets directly from disk and proxies /api/* calls to http://server:5000 internally. Nginx enforces request limits, headers, and routing.
  • CORS Simplification: Because Nginx serves both the frontend and proxies /api on the same origin (port 80), the browser never encounters cross-origin complications in production!
Nginx Ingress Reverse-Proxy Contract · nginx.conf 
server {
    listen 80;
    server_name localhost;

    # Serve static React client files
    location / {
        root /usr/share/nginx/html;
        index index.html index.htm;
        try_files $uri $uri/ /index.html;
    }

    # Proxy API requests to Express across internal Docker bridge
    location /api/ {
        proxy_pass http://server:5000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

The SSH Beginner Compromise vs. AWS Systems Manager (SSM)

Deliberate Educational Compromise

GitHub-hosted runner IPs come from large, dynamic public cloud ranges that change daily. You cannot easily restrict your EC2 Security Group port 22 to a single static IP without complex IP synchronizer scripts.

Our Hardened Compromise: We use direct SSH because it is the most approachable, transparent way to learn remote execution. We harden it by enforcing key-only authentication (disabling passwords completely), using a dedicated single-purpose deploy key, and verifying host keys with EC2_KNOWN_HOSTS to prevent man-in-the-middle attacks.

The Enterprise Alternative (AWS SSM): In larger production systems, teams replace SSH with AWS Systems Manager (SSM) and GitHub Actions OpenID Connect (OIDC). Actions requests a short-lived IAM token from AWS and sends commands over the AWS internal agent bus with zero open inbound ports on EC2. We keep SSH here so the remote execution steps remain visible and debuggable.

04 / Release Engineering · Safe Execution & Review

The Deployment Contract: Health Checks, Rollback & Stage 1 Gate

Deployment is not complete when containers start. A release is only complete when an automated health probe proves the new application responds successfully.

The Six-Step Deployment Dance

When code merges into main, GitHub Actions carries out these exact commands over SSH:

  1. Concurrency Lock: Workflow sets concurrency: production-deploy so two merges cannot execute simultaneously and overwrite release files.
  2. Preserve Previous State: Back up current release.env to release.env.bak on EC2.
  3. Write New Release Contract: Transfer docker-compose.prod.yml and write the new commit SHA to release.env (e.g. IMAGE_TAG=3a4b5c6).
  4. Pre-Pull Images: Run docker compose -f docker-compose.prod.yml pull to pull both private GHCR images before taking any container down.
  5. Recreate Services: Run docker compose -f docker-compose.prod.yml up -d. (Acceptable brief restart downtime as containers swap).
  6. Poll Health Endpoint: Loop curl -f http://localhost/api/health over SSH with retries and a timeout.

Automated Rollback Mechanics

If the health check fails (e.g. the server crashes on startup, a migration failed, or Neon rejected credentials), the deploy job does not abandon the broken container. It triggers an automated rollback script:

Automatic Rollback Concept · Deploy Step Script 
# Attempt health polling over SSH
if ! ssh $EC2_USER@$EC2_HOST "for i in {1..10}; do curl -f http://localhost/api/health && exit 0; sleep 3; done; exit 1"; then
  echo "::error::Health check failed! Initiating automatic rollback..."
  
  # Restore previous release tag and restart
  ssh $EC2_USER@$EC2_HOST "
    cd /opt/todo-app
    cp release.env.bak release.env
    docker compose -f docker-compose.prod.yml up -d
  "
  echo "::notice::Rolled back to previous release tag successfully."
  exit 1
fi
