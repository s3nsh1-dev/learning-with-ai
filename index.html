Stages 2, 3 & 4 Technical Glossary

  • E2E — End-to-End Testing: Complete full-stack verification where an automated browser clicks real UI elements wired to live containers.
  • CI — Continuous Integration: The automated practice of running unit, integration, and E2E suites on every pull request before code merges.
  • CD — Continuous Delivery: The automated packaging and deployment of verified code to registry and staging or production servers.
  • PR — Pull Request: A proposed code change from a branch or fork waiting for automated verification and peer review before merge.
  • GHCR — GitHub Container Registry: GitHub's private OCI registry hosted at ghcr.io for storing and distributing versioned Docker images.
  • OCI — Open Container Initiative: Open industry standards for container image formats, layers, and registry distribution specifications.
  • SHA — Commit Hash (40-char): The cryptographic unique identifier of a specific Git commit; used for immutable container image tags.
  • GHA — GitHub Actions: GitHub's workflow automation runner system executing jobs inside isolated Linux virtual machines.
  • GITHUB_TOKEN — Automatic Scoped Token: A temporary credentials token generated per workflow run with granular, explicit permissions.
  • Buildx — Docker BuildKit CLI: Docker's advanced builder offering parallel multi-stage building, cross-platform compilation, and cache backends.
  • TCP — Transmission Control Protocol: The underlying networking protocol over which the test runner connects to PostgreSQL port 5432 or 5433.
  • FIFO — First-In, First-Out: Sequential ordering guarantee essential when processing database seed queues or teardown hooks.
  • UUID — Universally Unique Identifier: Random 128-bit labels used to isolate test records so parallel test workers never overwrite each other.
  • SQL — Structured Query Language: Database command language used for migrations, seed data, and table truncation during cleanup.
  • ORM — Object-Relational Mapping: Database abstraction layer (like Prisma or Drizzle) that handles schema migrations and test queries.
  • HTTP — Hypertext Transfer Protocol: Request-response protocol validated by assertion checks on status codes like 200, 201, 400, or 404.

01 / Hermetic Boundaries · The Blast Radius

Why Tests Must Never Touch Neon Production Data

In naive beginner projects, integration tests often read from the same DATABASE_URL configured in the developer's .env file. If that environment points to Neon cloud storage, running a test suite becomes an active operational hazard.

When automated tests interact with a shared or live cloud database, three critical failures occur immediately:

  • Production Data Corruption: If a test runs DELETE FROM todos or truncates tables during teardown, real user records or staging data disappear.
  • Race Conditions & Flakiness: When two developers (or two parallel GitHub Action runner jobs) run tests simultaneously, their inserts and deletes collide. Test A expects 3 todos, but finds 7 because Test B just ran.
  • Network Latency & Rate Limits: Hitting a remote cloud database across the internet introduces TLS handshakes, network jitter, connection pool exhaustion, and serverless cold starts that double test execution time.
Test Architecture Comparison:
Scenario: Shared Database Pitfall — Test runners collide against the same remote cloud database. Data leaks, tests intermittently fail, and production tables are exposed to destructive teardown queries.
The Principle of Hermetic Testing

A test suite is hermetic when it is completely self-contained. It brings up its own isolated database, seeds its own schema, runs its tests, and tears down all resources without relying on or affecting anything in the outside world.

02 / Infrastructure · Disposable Containers

Provisioning Throwaway Databases with Docker Compose

The word ephemeral means "lasting for a very short time." In our CI/CD pipeline, an ephemeral database exists only for the duration of the test job and is completely wiped clean when the test finishes.

Instead of installing PostgreSQL on the host machine or relying on remote services, we use a dedicated test Compose file (docker-compose.test.yml) or Docker command that runs an official postgres:16-alpine container.

The PostgreSQL Readiness Race Condition

A common trap when launching a database container in CI is trying to connect immediately. When Docker starts the PostgreSQL container, Docker reports the container as "running" within milliseconds. However, the internal PostgreSQL database daemon needs several seconds to initialize database clusters and open socket listeners.

If your test script runs pnpm db:migrate before the database is ready, the migration immediately crashes with:

Terminal Error · Connection Refused Race Condition 
Error: connect ECONNREFUSED 127.0.0.1:5433
    at TCPConnectWrap.afterConnect [as oncomplete] (node:net:1606:16)
    at runMigrations (src/db/migrate.ts:14:9)
Process exited with code 1

To prevent this race condition, we must wait for PostgreSQL's built-in pg_isready health tool before starting the test runner:

Compose Service Definition · docker-compose.test.yml 
version: "3.8"

services:
  test-db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: test_user
      POSTGRES_PASSWORD: test_password
      POSTGRES_DB: todo_test_db
    ports:
      # Map to custom host port 5433 to avoid clashing with local Postgres (5432)
      - "5433:5432"
    # In-memory tmpfs makes tests 5x faster and leaves no disk artifacts
    tmpfs:
      - /var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U test_user -d todo_test_db"]
      interval: 2s
      timeout: 2s
      retries: 10
Why tmpfs (In-Memory Storage) Matters for Tests

By mounting tmpfs: /var/lib/postgresql/data, PostgreSQL writes database records directly to RAM instead of writing to disk. This speeds up test transactions significantly and guarantees that when the container exits, all data vanishes with zero disk cleanup required.

03 / Quality Assurance · The Exit Code Contract

Replacing Console-Only Logs with True Failing Assertions

The single most dangerous test suite is one that logs errors to the screen but still exits with status code 0 ("Success"). In CI/CD, if your test script does not return an exit code other than 0, GitHub Actions considers the job green and passes the pull request!

The "Silent Pass" Anti-Pattern

Look at how naive integration tests are frequently written:

Broken Test Script · Logs Errors but Exits with 0 
// ❌ ANTI-PATTERN: Silent Pass
async function testCreateTodo() {
  try {
    const res = await fetch("http://localhost:5000/api/todos", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ title: "" }) // Invalid payload!
    });
    const data = await res.json();
    
    if (res.status !== 201) {
      console.log("Failed to create todo: status was " + res.status);
      return; // ⚠️ Function returns normally, exit code remains 0!
    }
  } catch (err) {
    console.error("Test encountered error:", err);
    // ⚠️ Error is swallowed! Node process finishes with exit 0.
  }
}
testCreateTodo();

When GitHub Actions executes the script above, it looks only at the Node.js process exit status. Because the error was caught and logged, the process exits with code 0. GitHub Actions paints a green checkmark next to the PR, completely unaware that the API failed!

The True Assertion Contract

Proper assertions must verify three distinct aspects of every operation and throw unhandled errors or call assert / expect so the process exits with code 1 on failure:

Validation Layer What Must Be Asserted Example Assertion
HTTP Status Code Ensure exact status code semantics (e.g. 201 Created vs 200 OK vs 400 Bad Request). assert.strictEqual(res.status, 201);
Response Payload Validate shape, data types, and returned fields (including generated IDs). assert.ok(data.id, "Expected returned todo to have an id");
Database Persistence Directly query the database to confirm the record was actually written to the table. const row = await db.query("SELECT * FROM todos WHERE id = $1", [data.id]);
assert.strictEqual(row.rows.length, 1);
Robust Integration Test · Fails Fast with Strict Assertions 
import assert from "node:assert/strict";
import { pool } from "../src/db.js";

export async function runIntegrationTests() {
  console.log("▶ Testing POST /api/todos creation...");

  const res = await fetch("http://localhost:5000/api/todos", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ title: "Walk the dog" })
  });

  // 1. Assert HTTP Status
  assert.strictEqual(res.status, 201, `Expected status 201, got ${res.status}`);

  const body = await res.json();
  
  // 2. Assert Body Structure
  assert.ok(typeof body.id === "string" || typeof body.id === "number", "Todo must have a valid ID");
  assert.strictEqual(body.title, "Walk the dog", "Todo title must match payload");
  assert.strictEqual(body.completed, false, "Todo must initialize as uncompleted");

  // 3. Assert Database Persistence
  const dbCheck = await pool.query("SELECT * FROM todos WHERE id = $1", [body.id]);
  assert.strictEqual(dbCheck.rows.length, 1, "Todo record must exist in PostgreSQL table");

  console.log("✔ POST /api/todos passed cleanly.");
}
04 / Lifecycle · Repeatability

Deterministic Test State: Sandboxes and Cleanup Hooks

A test suite must be able to run 100 times in a row and produce the exact same result every time. If running a test suite leaves leftover records in the database, the second test run will behave differently from the first.

Before, Each, and After: The Lifecycle Triangle

Repeatable testing relies on strict lifecycle hooks:

  1. Global Setup (beforeAll): Wait for database readiness, run SQL schema migrations, and prepare fresh tables.
  2. Per-Test Sandbox (beforeEach): Truncate tables or clear records so every single test case begins with a pristine, predictable table state.
  3. Per-Test Teardown (afterEach): Cancel ongoing async handles, close open sockets, and ensure no pending promises keep Node alive.
  4. Global Teardown (afterAll): Close the database connection pool (pool.end()). If you don't close the pool, the Node process will hang indefinitely waiting for the open socket!
Database Cleanup Hook · src/tests/setup.ts 
import { pool } from "../db.js";

// Truncate tables before each test case for isolation
export async function cleanDatabase() {
  await pool.query("TRUNCATE TABLE todos RESTART IDENTITY CASCADE;");
}

// Global teardown hook to prevent hanging process
export async function closeDatabase() {
  await pool.end(); // Closes all active client connections in the pool
}
The "Hanging CI Job" Pitfall

In Node.js, an open database connection pool keeps an active event loop socket open. If your test runner finishes all assertions but never invokes await pool.end(), the test process will sit frozen in GitHub Actions until the runner hits its 6-hour timeout limit!

05 / End-to-End · Docker Orchestration & Assessment

Running Playwright Against the Dockerized Stack

Unit tests verify individual JavaScript functions. Integration tests verify that Express talks to PostgreSQL. But only End-to-End (E2E) tests verify that the real browser can load the React bundle from Nginx, submit a todo via /api, and see it rendered on screen.

The Test Execution Pipeline Script

In Stage 2, our end-to-end test runner follows this exact sequence from a clean Git checkout:

  1. Build & Start Containers: Run docker compose -f docker-compose.test.yml up -d --build to launch Client, Express API, and Ephemeral PostgreSQL on test ports.
  2. Poll Health Endpoint: Wait for http://localhost:8080/api/health to respond with 200 OK before launching the browser.
  3. Run Playwright Headlessly: Playwright spins up headless Chromium, navigates to http://localhost:8080, types "Buy milk", presses Enter, and asserts that the new todo item appears in the DOM.
  4. Tear Down & Wipe Volumes: Run docker compose -f docker-compose.test.yml down -v. The -v flag is critical: it removes anonymous and named Docker volumes so no leftover database state persists on disk!
Full Test Pipeline Runner · package.json script 
# Executed by CI runner or developer terminal
"test:e2e": "docker compose -f docker-compose.test.yml up -d --wait && playwright test && docker compose -f docker-compose.test.yml down -v"
Stage 2 Knowledge Check · ELI5
Why must the CI test teardown command execute `docker compose down -v` with the `-v` flag instead of just `docker compose down`?

Stage 2 Acceptance Criteria Checklist

Verify that your test implementation meets all Stage 2 capstone requirements:

  • ✓ Tests never connect to or write against the production Neon database.
  • ✓ PostgreSQL is run in an isolated ephemeral container with tmpfs or volume wiping.
  • ✓ All assertions fail with non-zero exit codes when endpoints return unexpected statuses or shapes.
  • ✓ Database pools are closed cleanly so tests do not hang the CI process.
  • ✓ Playwright tests successfully execute against the full Dockerized stack (Client + Server + Ephemeral DB).
  • ✓ docker compose down -v leaves no orphaned containers or lingering volumes behind.

01 / Stage 3 · Trust Boundaries

The Pull-Request Gate & Workflow Triggers

Continuous Integration exists for one non-negotiable reason: unverified code must never enter the main branch. Before a single line of JavaScript or Docker configuration is merged, an automated gate must run every test in complete isolation.

In GitHub Actions, this boundary starts with workflow triggers in .github/workflows/ci-cd.yml. A common security and operational flaw in early pipelines is triggering the exact same jobs for pull requests and pushes to main. If an untrusted fork opens a pull request, running deployment credentials or pushing container tags would allow an external attacker to hijack your production release.

⚠️ The First Law of Pipeline Security

Pull requests from feature branches or external forks must run strictly in read-only verification mode. They must never receive registry publishing rights, SSH keys, or cloud infrastructure credentials.

The Interactive Pipeline Mechanism

Explore how the pipeline reacts across three distinct lifecycle events: a standard verification PR, an approved push to main, and a failing pull request that triggers the CI gate brake.

Pipeline Execution Mode:
Scenario: Pull-Request CI Gate — A developer opens PR #42. GitHub Actions triggers parallel verification jobs (lint, typecheck, integration tests with ephemeral Postgres, Playwright E2E). Status reports Green to GitHub UI. Publish and Deploy jobs are completely locked.

Trigger Configuration in YAML

Here is the foundation of our production pipeline configuration. It declares triggers for both pull requests (any branch targeting main) and direct pushes to main (such as when a PR is merged):

.github/workflows/ci-cd.yml (Triggers & Concurrency) 
name: CI/CD Pipeline

on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main

# Cancel in-progress runs when a new commit is pushed to the same PR branch
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

# Default runner to zero permissions unless explicitly granted per job
permissions: {}
💡 Why cancel-in-progress Matters

When a software engineer pushes three rapid commits to a pull request, running three full suites of headless Playwright tests costs compute time and burns runner concurrency. The concurrency block cancels the superseded runs immediately.

02 / Stage 3 · Execution Velocity

Fast Parallel Checks & Dependency Caching

A CI pipeline that takes 15 minutes to run is a pipeline developers will bypass. High-performing engineering teams organize verification into parallel independent jobs and leverage deterministic dependency caching.

In our Todo application, the frontend React Vite client and backend Express server live in the same repository, but have completely separate dependency trees. Rather than running linting, typechecking, and building in one monolithic serial script, we split them into parallel runner jobs.

Why We Cache the pnpm Virtual Store

Running pnpm install from scratch on every commit downloads hundreds of megabytes of packages over the internet. GitHub Actions provides actions/setup-node with built-in caching support keyed on pnpm-lock.yaml:

Execution Phase Cold Run (No Cache) Warm Run (GHA Cache Hit) Engineering Impact
pnpm install ~140 seconds ~6 seconds Restores packages from GitHub Actions internal cache SSD
pnpm lint && build ~35 seconds ~32 seconds Vite compiles production client bundles to dist/
Total Feedback Latency ~3 minutes < 40 seconds Developer gets immediate pull request feedback

The Client Verification Job

Notice the precise sequence: install pnpm via pnpm/action-setup, configure Node 24 with cache path, restore dependencies, and execute typecheck and build:

.github/workflows/ci-cd.yml (Client Verification Job) 
jobs:
  test-client:
    name: Verify Client
    runs-on: ubuntu-latest
    permissions:
      contents: read
    defaults:
      run:
        working-directory: client
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Install pnpm
        uses: pnpm/action-setup@v3
        with:
          version: 12.4.2

      - name: Setup Node 24 with pnpm Cache
        uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: 'pnpm'
          cache-dependency-path: client/pnpm-lock.yaml

      - name: Install Dependencies
        run: pnpm install --frozen-lockfile

      - name: Run Client Linter
        run: pnpm lint

      - name: Compile Client Bundle
        run: pnpm build
⚠️ The --frozen-lockfile Guarantee

In CI, always use pnpm install --frozen-lockfile. If a package was added to package.json without committing the updated pnpm-lock.yaml, the build fails immediately rather than silently resolving nondeterministic versions.

03 / Stage 3 · Test Isolation

CI Service Containers: Ephemeral PostgreSQL in Actions

In Stage 2, we learned why integration tests must never touch a shared cloud database like Neon. In GitHub Actions, instead of writing complex shell scripts to start and stop Docker containers manually, we declare native Service Containers.

GitHub Actions provides a top-level services: definition within any job. When configured, the runner starts the specified Docker container before any job step executes, bridges network ports, runs a health check, and automatically terminates the container when the job finishes.

Runner Networking & Health Probes

Because our runner jobs execute directly on the ubuntu-latest VM host, mapped service ports are reachable on localhost:5432. But databases require several seconds to initialize their internal tables and listen on their socket. If the test runner attempts to connect before PostgreSQL is ready, the job crashes immediately.

We eliminate this race condition using a native Docker health check:

.github/workflows/ci-cd.yml (PostgreSQL Service Definition) 
  test-server:
    name: Verify Server
    runs-on: ubuntu-latest
    permissions:
      contents: read
    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_USER: test_user
          POSTGRES_PASSWORD: test_password
          POSTGRES_DB: todo_test
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-timeout 5s
          --health-retries 5
          --tmpfs /var/lib/postgresql/data
    defaults:
      run:
        working-directory: server
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Install pnpm
        uses: pnpm/action-setup@v3
        with:
          version: 12.4.2

      - name: Setup Node 24 with Cache
        uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: 'pnpm'
          cache-dependency-path: server/pnpm-lock.yaml

      - name: Install Dependencies
        run: pnpm install --frozen-lockfile

      - name: Typecheck Server
        run: pnpm typecheck

      - name: Run Integration Tests
        env:
          DATABASE_URL: postgresql://test_user:test_password@localhost:5432/todo_test
        run: pnpm test:integration
💡 The --tmpfs Performance Optimization

Notice the --tmpfs /var/lib/postgresql/data option. It mounts the database storage directly in runner RAM instead of virtual disk. In-memory PostgreSQL writes are 4x faster, and every row vanishes into thin air when the job ends.

04 / Stage 3 · Automated Acceptance

Full-Stack Playwright E2E & Diagnostic Artifacts

Unit and integration tests prove that isolated functions and SQL queries work. But they cannot prove that the React client can actually render items fetched from the Express API in a real browser. The ultimate CI gate is an End-to-End (E2E) browser suite.

In Stage 2, we built Playwright tests that drive a headless Chromium browser against our containers. In GitHub Actions, we orchestrate the full stack directly inside the runner, verify the live health endpoint, execute the tests, and preserve diagnostic artifacts if any assertion fails.

Orchestrating the Stack in CI

The E2E job requires three coordinated components running simultaneously:

  1. PostgreSQL Service Container: Provides the clean database.
  2. Background API Server: Express running on port 5000 with pnpm start &.
  3. Playwright Test Runner: Spins up headless Chromium, hits port 5000 / 3000, and verifies user journeys.
.github/workflows/ci-cd.yml (Playwright E2E Job) 
  test-e2e:
    name: Full-Stack E2E
    runs-on: ubuntu-latest
    permissions:
      contents: read
    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_USER: test_user
          POSTGRES_PASSWORD: test_password
          POSTGRES_DB: todo_test
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-timeout 5s
          --health-retries 5
          --tmpfs /var/lib/postgresql/data
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Install pnpm & Node
        uses: pnpm/action-setup@v3
        with:
          version: 12.4.2

      - uses: actions/setup-node@v4
        with:
          node-version: 24

      - name: Install Server & Client Dependencies
        run: |
          cd server && pnpm install --frozen-lockfile
          cd ../client && pnpm install --frozen-lockfile
          cd ..

      - name: Install Playwright Browsers
        run: npx playwright install --with-deps chromium

      - name: Start Server in Background
        env:
          DATABASE_URL: postgresql://test_user:test_password@localhost:5432/todo_test
          PORT: 5000
        run: |
          cd server
          pnpm start &
          npx wait-on http://localhost:5000/api/health --timeout 20000

      - name: Run Playwright Tests
        run: npx playwright test

      - name: Upload Diagnostic Artifacts on Failure
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-failure-report
          path: playwright-report/
          retention-days: 7
🚨 The Diagnostic Failure Boundary

Notice if: failure() on the artifact upload step. When an E2E test fails in headless CI, you cannot look at the screen. Uploading the Playwright trace zip and screenshots gives the engineer video recordings and DOM snapshots of the exact instant the assertion failed.

05 / Stage 4 · Continuous Delivery

Publishing to GHCR: Credentials & Least Privilege

Once Stage 3's verification jobs pass, we transition from Continuous Integration (testing) to Continuous Delivery (publishing release artifacts). We publish our private client and server images to GitHub Container Registry (GHCR) at ghcr.io.

In legacy setups, developers frequently created long-lived Personal Access Tokens (PATs) and pasted them into repository secrets. This is an enormous security liability: if leaked, a PAT grants access to everything the developer owns. In modern GitHub Actions, we use the automatic, ephemeral GITHUB_TOKEN with granular, explicit permissions.

The Principle of Least Privilege in CI/CD

By default, we set top-level permissions: {}. In the publishing job, we grant only the two exact permissions required to pull the Git commit and publish container packages:

Permission Scope Granted Level Technical Rationale
contents read Allows checking out the merged commit code to build the Dockerfile
packages write Authorizes pushing image layers and manifests to ghcr.io
id-token, deployments, etc. none Eliminates unnecessary privilege attack vectors

The Release Boundary Condition

The publishing job must declare two guardrails: it must wait for all test jobs to succeed (needs: [...]), and it must execute only when code is merged into the trusted main branch:

.github/workflows/ci-cd.yml (GHCR Authentication & Guardrails) 
  publish-images:
    name: Build & Publish GHCR Images
    runs-on: ubuntu-latest
    needs: [test-client, test-server, test-e2e]
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    permissions:
      contents: read
      packages: write
    steps:
      - name: Checkout Merged Code
        uses: actions/checkout@v4

      - name: Log in to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
💡 Why needs: [...] is Critical

If you omit needs: [test-client, test-server, test-e2e], GitHub Actions will run the publish-images job in parallel with your tests! Broken code could be packaged and pushed to the registry before the test failure even registers.

06 / Stage 4 · Build Engineering

Docker Buildx Layer Caching & OCI Metadata

Building a Docker image from scratch inside CI is slow. If a developer only changed one line of CSS in the client, why should the runner re-download the Node base image and re-execute pnpm install?

With Docker Buildx and BuildKit, GitHub Actions can cache intermediate Dockerfile build layers directly inside GitHub's caching backend using type=gha. Subsequent runs reuse unchanged layers, reducing image build times from 3 minutes to 15 seconds.

Standard OCI Labels & Traceability

Every container image published to production should be self-documenting. Using docker/metadata-action, we extract Git metadata and embed standard OCI (Open Container Initiative) annotations:

  • org.opencontainers.image.source: Links the image directly back to the GitHub repo URL.
  • org.opencontainers.image.revision: Contains the exact 40-character Git commit SHA.
  • org.opencontainers.image.created: Timestamp of the build.
.github/workflows/ci-cd.yml (Buildx Layer Caching & Metadata) 
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Extract OCI Metadata for Client
        id: meta-client
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}-client
          tags: |
            type=sha,prefix=sha-,format=short
            type=raw,value=latest,enable=${{ github.ref == 'refs/heads/main' }}

      - name: Build and Push Client Image
        uses: docker/build-push-action@v5
        with:
          context: ./client
          push: true
          tags: ${{ steps.meta-client.outputs.tags }}
          labels: ${{ steps.meta-client.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
💡 What mode=max Does

Standard Docker caching only saves the final exported image layer. Specifying cache-to: type=gha,mode=max instructs BuildKit to cache layers from intermediate multi-stage build stages (such as the pnpm compilation container), maximizing cache hits on future commits.

07 / Stage 4 · Production Rigor

Immutable Commit SHA Tags & Pipeline Review

The single most dangerous anti-pattern in container deployment is deploying :latest. In this final topic, we establish why immutable commit SHA tags are essential, and review the complete, unified delivery pipeline.

The "Latest" Trap vs Immutable Releases

When you tag a Docker image as latest, you are creating a mutable, moving target:

Dimension The :latest Anti-Pattern Immutable SHA Tag (:sha-e8f91c0)
Determinism Ambiguous. Which Git commit does this container run? Nobody knows without running inspection commands. Cryptographically absolute. The tag matches the exact Git commit SHA in the repository history.
Rollback Safety Impossible. Rolling back means re-tagging or guessing which version was previously deployed. Instant. Changing one environment variable (IMAGE_TAG=sha-a1b2c3d) rolls back cleanly.
Docker Daemon Caching Host may skip pulling if a local image tagged latest already exists on disk. Every commit is a brand-new unique tag. docker compose pull always retrieves the exact release.
