Question one · address

The phone test proved something about Vite, not about laptops

You asked

How does a laptop’s localhost make the port available at network level? When I try to open the Vite server on my phone on the same wifi, nothing happens. So why the concern, why the protection?

Your phone failed because Vite chose to be unreachable. Docker chooses the opposite. Same laptop, same wifi, two different defaults — and the choice is one number, written down when the program opens its socket.

A program that wants to accept connections has to name an address to accept them on. Your laptop has more than one. Right now it has a loopback wire that only it can talk to, and a wifi wire with the address 192.168.1.12 that your router gave it. Choosing 127.0.0.1 means “only the loopback wire.” Choosing 0.0.0.0 means “every wire I have, including the ones I join later.”

The same three sockets, measured on your machine just now

$ ss -ltn                       # every socket listening, and the address it took
LISTEN  [::1]:5173        ← vite, default settings
LISTEN  127.0.0.1:8082    ← docker run -p 127.0.0.1:8082:80
LISTEN  0.0.0.0:8081      ← docker run -p 8081:80        (no prefix)

$ curl 192.168.1.12:8081        # the laptop's wifi address, not localhost
HTTP 200

$ curl 192.168.1.12:8082
connection refused

$ curl 192.168.1.12:5173        # what your phone was doing
connection refused

Three containers, one flag of difference, three different answers. The one without the prefix answered on the address your phone would have dialled. Note that -p 8081:80 and -p 0.0.0.0:8081:80 are the same instruction — leaving the address off does not mean “no address,” it means “all of them.”

So why care, when it’s only your flat?

There is also a difference in what is behind the door. A stranger reaching Vite reads the HTML you were going to publish anyway. A stranger reaching 5432 gets a Postgres login prompt, and the password it wants is sitting in your .env — the same one you probably used on two other projects. That is why the brief singled out the database and not the api.

The part that surprises people: your firewall is not covering this

Answer to question one

Localhost is not a property of the laptop, it is a choice each program makes when it starts listening. Vite chose loopback, which is why your phone saw nothing. Docker chooses every wire unless the line says otherwise. "127.0.0.1:5432:5432" is you making Docker's choice for it.

Question two · folder

The collector is your app again, woken by a clock instead of a visitor

You asked

I do not understand this concept of collector. And why does the collector have the same volumes as the api, especially ./frames:/var/lib/rainfall/frames? I have read compose files online and none of them have this pattern on volumes.

There are two ways a program gets work. Somebody asks it, or a clock tells it. The api is the first kind. The collector is the second kind. They are the same codebase; the only difference is who wakes them up.

Why not just do the fetching inside the api?

Because a web server that stops to download a three-megabyte radar frame is a web server answering nobody for the length of that download. Because if you ever run two copies of the api to handle load, you get two collectors, two copies of every frame and two rows per timestamp. And because when the upstream feed goes down, you want the thing that crash-loops to be the collector while the archive keeps serving. Splitting them costs you one extra service and buys all three.

Now the volume: they are not two copies, they are one folder

./frames is a bind mount, so it is a real folder in your repository that appears inside both containers at /var/lib/rainfall/frames. Not a copy in each. The same bytes on the same disk, seen through two doors. The collector writes a .png into it; the api reads that same .png out of it. That handover is the entire architecture, and the shared line is what makes it possible.

Here is that shared folder actually working, run just now: a container writing frames on a loop, a second container listing the same path, and your own shell listing the folder on disk. Three viewpoints, one set of files. 

# what the api container sees at /var/lib/rainfall/frames
frame-1.png  frame-2.png  frame-3.png  frame-4.png  frame-5.png

# what you see in ./frames on the laptop, the same instant
frame-1.png  frame-2.png  frame-3.png  frame-4.png  frame-5.png

# and the contents, read from the api container, written by the collector
$ docker exec api cat /var/lib/rainfall/frames/frame-1.png
radar frame 1

The other shared mount, ./api:/app, is there for the same reason at a different level. Both services run your source from your folder, so editing one file changes both. Drop it from the collector and the collector runs whatever code was baked into the image at build time, silently drifting from the api it is supposed to match.

Why you have never seen this online

Answer to question two

A collector is your app started with a different command:, doing the work nobody asks for. It repeats the api's volumes because it is the same app — ./api so it runs the same code, ./frames so the file it writes is the file the api serves. Take that second line away and both services keep running perfectly while the site stays empty.

Question three · moment

.env is the one file Compose opens without being told

You asked

How are we getting WEB_PORT when we are not declaring the env_file?

Because env_file: was never going to supply it. Those are two different machines that happen to share a word. One fills in blanks in the text of your compose file; the other puts variables inside a running container. They happen at different times and neither can do the other's job.

Compose does two separate things when you type up. First it reads compose.yaml as plain text and replaces every ${...} — no container exists yet, the daemon has not been asked for anything. For that step it looks in your shell's environment, and in a file called .env sitting next to the compose file. It opens that file automatically. There is no line to write, which is exactly why you could not find one.

The proof: one variable name, two values, one file

Here is a compose file that uses both mechanisms on the same name at the same time. The port asks for ${WEB_PORT}; the service also loads .env.web, which sets WEB_PORT to something else entirely. 

services:
  web:
    image: nginx:alpine
    env_file: .env.web          # this file says WEB_PORT=9999
    ports: ["${WEB_PORT}:8000"]   # .env says WEB_PORT=4000

What happens when .env is missing

Delete .env and keep everything else. The container still gets its WEB_PORT=9999 from env_file, so nothing about the container changes. The published port simply disappears from the rendered file, and Compose says so in a warning rather than an error — up carries on and starts the stack. 

$ rm .env && docker compose config
warning  The "WEB_PORT" variable is not set. Defaulting to a blank string.

services:
  web:
    environment:
      WEB_PORT: "9999"      ← still here, env_file did its job
    ports:
      - target: 8000
        protocol: tcp     ← published: is gone. no port. no error.

That warning is the whole failure mode: your site is unreachable on localhost:4000, the container is healthy, the logs are clean, and the only hint scrolled past during up. It is also why the drill at the bottom of your own compose file says to run docker compose config first — that command is how you see what moment one decided, before moment two acts on it.

Your own file, rendered right now

There is no .env in this repository — it is in .gitignore and was never created. So moment one has nothing to substitute, and running docker compose config against your docker-compose.yml this minute produces thirteen warnings and a document that is already broken in three places, before a single container exists. 

$ docker compose config
warning  The "WEB_PORT" variable is not set. Defaulting to a blank string.
warning  The "POSTGRES_PASSWORD" variable is not set. Defaulting to a blank string.
          ... eleven more like it ...

  api:
    environment:
      DATABASE_URL: postgresql://:@db:5432/   ← no user, no password, no database name
    ports:
      - target: 8000                        ← published: absent. the site has no port.

  db:
    image: 'postgres:'                     ← a tag that cannot be pulled
    ports:
      - host_ip: 127.0.0.1                 ← survives: it was typed, not interpolated
        published: "5432"

Nothing here is wrong with the YAML you wrote. The file is fine; the value source is absent. Notice which line survived: 127.0.0.1 is literal text, so moment one had nothing to do to it. Everything that came from ${...} is now an empty string. Write a .env beside the compose file with the five names it asks for and every one of those lines fills in.

Answer to question three

You are getting WEB_PORT from .env, which Compose opens by itself because of where it sits, not because anything points at it. That is also why POSTGRES_PASSWORD in your file can be both interpolated into DATABASE_URL and handed to db as an environment variable — two mechanisms, one source file, written once.
