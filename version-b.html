Docker Compose · Part 2

Write the compose file

Part 1 showed what the file is. This part types one from an empty screen: seven keys, the five commands you run every day, and the one line that lies to you.

The shape of it

One file, two running things

You describe the containers you want. Compose makes them, and puts them on a private network of their own.

Key 1 · where it comes from

image or build, never both

Every service needs a filesystem to start from. There are two ways to get one.

Build runs once

Edit your Dockerfile or requirements.txt, run up -d again, and Compose silently reuses the old image. You get no warning and no error — just old code. Ask for the rebuild: docker compose up -d --build.

Key 2 · reaching in

Ports: a door in the wall

A container is sealed. ports cuts exactly one door so your browser can get through.

Our db has no ports at all

It does not need one: web reaches it across the private network. Publishing "5432:5432" exposes Postgres to everything that can see your machine. If you really want a GUI client on it, bind it to yourself only: "127.0.0.1:5432:5432".

Key 3 · settings

Two ways to hand over a value

A container starts knowing nothing about your machine. Configuration arrives as environment variables.

environment:

Values written into the compose file. Anyone reading the file sees them, which is fine for a port, a log level, a hostname.

env_file:

Points at a file of KEY=value lines. Compose reads it and passes every line in. This is where passwords go, because that file stays out of git. 

# .env.db  — gitignored
POSTGRES_USER=app
POSTGRES_PASSWORD=s3cret
POSTGRES_DB=appdb

# compose.yaml
  db:
    image: postgres:16
    env_file: .env.db

  web:
    environment:
      DATABASE_URL: postgresql://app:s3cret@db:5432/appdb

Read the last line slowly. The host in that URL is db — the service name from figure one, doing its job.

Same name, different job

A file called plain .env next to your compose file is not handed to any container. Compose reads it while parsing the YAML, to fill in blanks you wrote as ${LIKE_THIS}. One file configures containers, the other configures the file itself.

Key 4 · keeping things

Volumes: the two kinds of storage

Everything a container writes vanishes when the container is removed. A volume is how bytes escape that.

The name you write twice

services:
  db:
    volumes:
      - pgdata:/var/lib/postgresql/data   # 1. use it

volumes:                                   # 2. declare it
  pgdata:
If you skip the second one

Compose refuses to start: service "db" refers to undefined volume pgdata. The service line says mount this; the top-level block says this exists. Requiring both turns a typo into an error rather than a silently empty database.

Key 5 · after a crash

What restart actually promises

Containers exit. This is your standing instruction for when they do.

You write App crashes You reboot the laptop You ran stop
no stays down stays down stays down
on-failure restarts stays down stays down
unless-stopped restarts comes back stays down
always restarts comes back comes back anyway

The last column is the entire difference between the bottom two. always overrules you: it starts again on the next boot even though you deliberately stopped it. unless-stopped is the one you want.

Key 6 · the trap

The line that lies to you

depends_on: [db] reads like wait for the database. It means start db first, and then it stops caring.

Make db prove it is ready

  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 2s
      retries: 15
      start_period: 5s

  web:
    depends_on:
      db:
        condition: service_healthy

pg_isready already ships inside the Postgres image, so there is nothing to install. You need both halves: the healthcheck is what makes db healthy rather than merely running, and the condition is what makes web wait for it. Either one alone changes nothing.

Key 7 · identity

Whose containers are these?

Compose stamps a project name on everything it creates, and by default that name is just the folder you happen to be standing in. 

$ pwd
/home/you/myapp

$ docker compose ps
NAME              SERVICE   STATUS
myapp-web-1       web       running
myapp-db-1        db        running

$ docker volume ls
myapp_pgdata

Rename the folder and Compose stops recognising the containers it started; you quietly get a second set, and the old volume keeps your data hostage under the old name. Pin it with a top-level name: myapp and it no longer depends on where the folder lives.

Filling blanks with .env

# .env — next to compose.yaml
TAG=16
WEB_PORT=8000

# compose.yaml
  db:
    image: postgres:${TAG}
  web:
    ports:
      - "${WEB_PORT}:8000"

Before debugging anything else, look at what Compose actually read: docker compose config prints the file with every blank filled in and every default made explicit.

Every day

Five commands and one loop

Stopping, and the difference that costs you data

Command Containers Named volume pgdata Bind mount ./app
stop stopped, still there kept kept
down removed kept kept
down -v removed deleted kept

The last column never changes: ./app is your folder, not Docker's, so no Compose command can remove it. The middle column is where your rows live, and -v is four keystrokes away from deleting them.

All together

The finished file

name: myapp

services:
  web:
    build: .
    ports:
      - "${WEB_PORT}:8000"
    environment:
      DATABASE_URL: postgresql://app:s3cret@db:5432/appdb
    volumes:
      - ./app:/app
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:${TAG}
    env_file: .env.db
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 2s
      retries: 15
      start_period: 5s
    restart: unless-stopped

volumes:
  pgdata:

Read it back to yourself

  1. Point at the two places pgdata appears and say what each one is doing.
  2. Which half of "${WEB_PORT}:8000" is your laptop?
  3. Why does db work with no ports line at all?
  4. A colleague's web crashes on a cold laptop with depends_on: [db] already present. Name the two keys that fix it.
  5. You edited requirements.txt and ran up -d. Why is nothing different?
  6. Which stop command destroys your rows, and which one keeps them?

Left out on purpose, roughly in the order you will need them: profiles: for services only some people run, several -f files layered for dev against prod, and a top-level networks: block for when one network stops being enough.
