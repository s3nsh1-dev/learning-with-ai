Acronym Reference & Core Definitions

  • HMR (Hot Module Replacement): Updating running browser JS/CSS in milliseconds via WebSockets without full page reload.
  • Bind Mount: Directly mapping a host folder (e.g. ./client:/app) into a container so file edits reflect immediately.
  • PAT (Personal Access Token): A long-lived GitHub user credential. Dangerous if granted broad permissions.
  • Fine-Grained Token: A modern GitHub token scoped strictly to single repositories with minimal permissions (e.g. read:packages).
  • GHCR (GitHub Container Registry): The OCI registry (ghcr.io) where private Docker images are published and pulled.
  • chmod 600: Linux file permission setting: Read/Write by file owner only; zero access to all other users.
  • Immutable Artifact: A container image that is frozen at build time and never modified at runtime.

Hot Reloading Mechanics vs. Immutable Images & The Role of EC2 Registry Tokens

A developer-first guide explaining what powers instant hot reloading in local Docker Compose, why hot reloading is strictly excluded from production GHCR images, and why an EC2 server uses a scoped read-only token to pull private containers.

Topic 01 · First Principles & Quick Reference

What is Hot Reloading (HMR)?

Before looking at Docker bind mounts or registry security, we must understand the fundamental question: What actually is Hot Reloading, and why was it invented?

The Fundamental Definition

Hot Reloading (technically known as Hot Module Replacement, or HMR) is a development capability where code changes in your source files (JavaScript, TypeScript, JSX, CSS) are injected into the live running browser application in milliseconds without performing a full browser page refresh.

The 3 Eras of Frontend Developer Feedback

To appreciate what Hot Reloading does, compare the three ways web code updates reach a developer's browser:

Method How It Works What Happens to State (Inputs, Modals, Filters) Feedback Speed
1. Manual Reload You edit code, wait for a manual rebuild, switch to the browser, and press F5. 100% Wiped — DOM is destroyed, JS restarts from line 1. Slow (5–15 seconds)
2. Live Reload A file watcher detects file saves and automatically triggers window.location.reload(). 100% Wiped — Automates the reload, but still destroys all page state. Medium (1–3 seconds)
3. Hot Module Replacement (HMR) The dev server compiles only the changed file and pushes a delta patch over a WebSocket. The browser swaps the module in live RAM. 100% Preserved — Typed text, open dialogs, and navigation state stay intact! Instant (< 50 ms)

The Killer Feature: Preserving UI State

Imagine you are testing a complex checkout wizard on Step 4. You have filled out 12 input fields, chosen a dropdown option, and opened a verification modal. You notice the submit button has bad padding or a typo.

  • With full reload: You fix the typo, the browser reloads to Step 1, all 12 input fields are wiped, the modal closes, and you must waste 30 seconds clicking back to Step 4 to see if the button looks right.
  • With Hot Reloading: You fix the typo in your editor. In 40 milliseconds, the button text updates right on your screen. The modal stays open, your 12 filled input fields remain filled, and your cursor does not move.

Quick Answers: The Two Big Project Questions

Question 1: What enables instant hot reloading in Docker, and why is its absence in GHCR good?

• In local development: Hot reloading is enabled by a Host Bind Mount (volumes: - ./client:/app) connecting your laptop folder to the container, Linux kernel inotify file watchers, Vite's in-memory HMR compiler, and a persistent WebSocket connection to your browser.

• Why its absence in GHCR is good: GHCR creates Immutable Production Artifacts. In production, we do not want a heavy Node.js development server running. We want lightweight, battle-hardened Nginx serving pre-compiled static files from /dist. This drops RAM usage from 350MB to 15MB, prevents memory leaks, stops configuration drift, and ensures rock-solid deterministic deployments.

Question 2: What is the role of the read-only token on EC2, why is PAT bad, and where is it kept?

• Role: Our GHCR container images are private packages. EC2 must authenticate with ghcr.io to pull them during deployment.

• Why PAT is bad: A classic Personal Access Token has broad account-level permissions (repos, billing, organization access). If an EC2 server gets compromised, an attacker stealing a classic PAT gets full control over your GitHub account.

• Why Fine-Grained Read-Only Token is good: It follows the Principle of Least Privilege. It is scoped strictly to read:packages on this single repository. Even if an attacker steals it, they can only download the image—they cannot push code or touch repositories.

• Where it is kept and secured: Stored on the EC2 host in ~/.docker/config.json locked down with Linux file permissions (chmod 600), accessible solely by the root/docker user.

Topic 02 · Developer Ergonomics

What Enables Instant Hot Reloading in Development

When you edit a React component (e.g. App.tsx) on your laptop while running Docker, how does the browser update in 50 milliseconds without running docker build? Hot reloading is powered by the coordination of three distinct mechanisms:

Mechanism 1: The Docker Bind Mount (Shared Storage)

In a development Compose file, you define a volume mount:
volumes: - ./client:/app (or ./client/src:/app/src)
A bind mount bypasses the container's internal filesystem and directly maps your laptop's folder into the container. When your code editor saves a file to disk on your Mac/Linux laptop, that exact file byte changes inside the container at the same microsecond.

Mechanism 2: Linux Inotify / File System Watchers

Inside the container, Vite is running in development mode (pnpm dev). Vite keeps an active file watcher on /app/src using Linux kernel inotify events. The moment the bind mount delivers the edited file, Vite detects the modified timestamp.

Mechanism 3: WebSocket Hot Module Replacement (HMR)

Instead of forcing a full browser refresh (which wipes form inputs and state), Vite re-compiles only the single changed component in memory. It then sends an updated JavaScript snippet across a persistent WebSocket connection to your browser:
WebSocket → Browser Client → React Fast Refresh re-renders the component in the DOM.

Why We Love This in Development

  • Zero Build Lag: Without bind mounts, every CSS tweak or button fix would require running docker build (taking 2–3 minutes).
  • Preserved State: You don't lose typed form inputs, open modals, or navigation state while iterating on code.
  • Fast Feedback Loop: Bugs are caught immediately as you write code.
Topic 03 · Production Hardening

Why Its Absence in GHCR Images is Good (and Necessary)

If hot reloading is so fast, why don't we put it on EC2? Because in production, hot reloading is a dangerous anti-pattern. Here is why omitting hot reloading from GHCR images is essential engineering:

1. The Principle of Immutable Artifacts

In production, you need absolute certainty: What code is running on the server?
In GHCR, our client image contains pre-compiled, static assets baked into /usr/share/nginx/html at build time. The container image is tagged with the exact Git commit SHA (e.g. sha-b94f0e5). If EC2 used bind mounts and hot reloading, developers could SSH into the server and edit files live on disk. That creates Configuration Drift: your server is running rogue code that exists nowhere in Git!

2. Nginx vs. Vite Dev Server (Massive Performance & Stability)

• Vite Dev Server (Node.js): Designed for one developer on a laptop. It uses heavy RAM, parses TypeScript on the fly, and leaks memory over time if left running for weeks under high concurrent traffic.
• Nginx (Production Container): Written in highly optimized C. It consumes less than 15 MB of RAM, handles tens of thousands of concurrent HTTP requests, and serves pre-gzipped static files with zero CPU overhead.

3. Security & Container Isolation

A bind mount breaks container isolation by linking the host's physical filesystem directly into the container. If an attacker exploits a vulnerability in a web application with a host bind mount, they can overwrite files on the EC2 host disk (Container Escape). In contrast, our GHCR image runs with read-only baked files and no access to the host disk.

Topic 04 · Registry Authentication

The Role of the Read-Only Token on EC2

You asked: "what is the role of GIT_TOKEN in all these EC2 ghcr image kind of process. i learned that using PAT is bad but TOKEN is good but i am not sure why are we using this token and where its kept and actually secure"

1. Why Does EC2 Need a Token at All?

By default, images published to GitHub Container Registry (GHCR) in your private repository are private packages. If you log into your EC2 instance and run:
docker pull ghcr.io/s3nsh1-dev/docker-beginner-simulation-client:sha-b94f0e5
GitHub will reject the request with Error response from daemon: Head "...": unauthorized. EC2 must prove its identity to GitHub before it is allowed to download the container layers.

2. Why Can't EC2 Use the GitHub Actions GITHUB_TOKEN?

In Stage 4, our CI pipeline used secrets.GITHUB_TOKEN to push images. Why can't we copy that token to EC2?
Because secrets.GITHUB_TOKEN is ephemeral: it is dynamically minted by GitHub when a workflow run begins, and it is destroyed the instant the workflow finishes! It has a lifespan of only a few minutes. It physically does not exist when EC2 wants to pull the image hours or days later.

3. The Token Hierarchy: Why Classic PAT is Dangerous vs. Scoped Token

Token Type Permission Scope Blast Radius if Server is Hacked Verdict
Classic PAT (Broad) repo, admin:org, delete:packages, user Attacker can delete repositories, read private source code, modify billing, and push malicious commits. CRITICAL RISK
Actions GITHUB_TOKEN Job-scoped, ephemeral Lives only inside CI runner VM; cannot be placed on EC2. CI ONLY
Fine-Grained Read-Only Token read:packages on docker-beginner-simulation ONLY Attacker can only download the Docker image. Zero write access, zero repo access, zero account control. RECOMMENDED (Least Privilege)
The Principle of Least Privilege in Action

Notice the beauty of this security boundary:
Even if a rogue actor completely breaches your EC2 server and steals the token, they cannot harm your project! The token cannot push backdoored images to GHCR, cannot view other repositories, and cannot delete your packages. It is a strictly read-only key.

Topic 05 · Secret Storage & Verification

Where the Token Lives on EC2 & How It Is Secured

How does Docker on EC2 store the token, and how do we prevent unauthorized users on the machine from reading it?

1. What Happens During docker login

During server provisioning in Stage 6, you execute:

EC2 Host Shell 
echo "$GHCR_READ_TOKEN" | docker login ghcr.io -u s3nsh1-dev --password-stdin

When this command runs, Docker contacts ghcr.io, verifies the credentials, and writes an authentication header into a config file on the EC2 host:
/home/ubuntu/.docker/config.json (or /root/.docker/config.json).

2. How the Token is Kept Secure on EC2

The 3 Layers of Host Security

1. Linux File Permissions (chmod 600): The .docker/config.json file is given permission 600 (read and write exclusively by the file owner). Any non-root user or web process on the machine is blocked by the Linux OS kernel from opening the file.

2. Strict Secret Boundary: The token is never baked into Dockerfiles, never committed to Git, and never injected into container environment variables. It stays on the EC2 host OS, used solely by the Docker daemon to pull images.

3. SSH Key-Only Server Access: In Stage 6, password authentication on EC2 is completely disabled. Only administrators possessing the verified SSH private key can connect to the instance.

Development Flow: Bind mounts map laptop source files directly into Vite dev server. Edits update the browser in milliseconds without container rebuilds.

Topic 06 · Operations & Runbook

Setting Up the Production EC2 Environment from Scratch

You have created an Ubuntu 24.04 LTS EC2 instance on AWS, you have your SSH private key (.pem), and you generated your GitHub Classic PAT with read:packages. Docker is not installed yet. Here is the step-by-step engineering runbook to turn this bare machine into a secure, hardened, automated Docker production host.

The Target Architecture on EC2

• Host OS: Ubuntu 24.04 LTS x86_64
• Container Engine: Docker Engine & Docker Compose plugin (v2) from Docker's official apt repository.
• App Root: /opt/todo-app (owned by user ubuntu).
• Network Boundary: Port 80 (HTTP) public $\rightarrow$ Nginx container. Port 5000 (Express API) strictly internal $\rightarrow$ unreachable from the Internet.
• Registry Credentials: Stored in ~/.docker/config.json with permission 600.
• Database Secret: Stored on the host in /opt/todo-app/server.env with permission 600.

Step 1: Verify AWS Security Group (Firewall Rules)

Before touching the terminal, confirm your EC2 instance's Inbound Security Group Rules in the AWS Console:

Type / Protocol Port Range Source Purpose & Security Justification
SSH (TCP) 22 My IP (e.g. x.x.x.x/32) Restricts remote shell management strictly to your laptop. Never leave SSH open to 0.0.0.0/0.
HTTP (TCP) 80 0.0.0.0/0 Public web visitors connect to Nginx. Nginx handles routing and serves static SPA assets.
Custom TCP (Port 5000) 5000 DO NOT ADD (CLOSED) The Express server communicates with Nginx inside Docker's internal virtual bridge network. It must never have a public host port.

Step 2: Connect to Your EC2 Instance via SSH

On your local laptop terminal, ensure your downloaded AWS key pair has strict read-only permissions (OpenSSH will refuse to use a key that is readable by other users):

Laptop Local Terminal 
# 1. Lock down key file permissions
chmod 400 ~/.ssh/your-ec2-key.pem

# 2. Connect to the EC2 public IPv4 address
ssh -i ~/.ssh/your-ec2-key.pem ubuntu@<EC2_PUBLIC_IP>

Step 3: Install Docker Engine & Compose v2 (Official Repos)

Why NOT sudo apt install docker.io?

Ubuntu's default docker.io package is frequently months or years out of date, lacks the modern Compose V2 CLI plugin (docker compose), and misses performance fixes. Always configure Docker's official APT repository directly.

Run the official installation script on your EC2 instance:

EC2 Shell · Install Docker Engine 
# Update system packages & install prerequisites
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg

# Add Docker's official GPG signing key
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Add the repository to Apt sources
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# Install Docker Engine, CLI, and Compose v2 plugin
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# Verify installation
docker --version
docker compose version

Step 4: Grant Non-Root Docker Permissions

By default, the Docker daemon binds to a Unix socket owned by root. Add the default ubuntu user to the docker group so deployment commands run without sudo:

EC2 Shell · Group Setup 
sudo usermod -aG docker ubuntu
newgrp docker

# Test that docker runs cleanly without sudo:
docker ps

Step 5: Create the Deployment Directory (/opt/todo-app)

Under the Linux Filesystem Hierarchy Standard (FHS), /opt is the designated location for self-contained, add-on application software. Create the directory and assign ownership to ubuntu:

EC2 Shell · App Directory 
sudo mkdir -p /opt/todo-app
sudo chown -R ubuntu:ubuntu /opt/todo-app
cd /opt/todo-app

Step 6: Authenticate with GHCR (Using Your Read-Only Token)

Now use the Classic Personal Access Token (with only read:packages) that you generated earlier. Pipe it to docker login via stdin so the token is never logged in your shell history:

EC2 Shell · Registry Authentication 
# Replace <YOUR_CLASSIC_PAT> with your actual ghp_... token:
echo "<YOUR_CLASSIC_PAT>" | docker login ghcr.io -u s3nsh1-dev --password-stdin

# Secure the Docker credentials file on disk:
chmod 600 ~/.docker/config.json
What Just Happened?

Docker contacts ghcr.io, validates the token, and writes an authentication entry to ~/.docker/config.json. Running chmod 600 ~/.docker/config.json ensures only the ubuntu user can read this file.

Step 7: Decouple Runtime Secrets (Create server.env)

In Stage 5, we designed our architecture so the production Express container reads its database connection from a host-only environment file. Create /opt/todo-app/server.env with your production Neon PostgreSQL URL:

EC2 Shell · Write server.env 
cat << 'EOF' > /opt/todo-app/server.env
DATABASE_URL="postgresql://user:password@ep-xyz.us-east-2.aws.neon.tech/neondb?sslmode=require"
PORT=5000
NODE_ENV=production
EOF

# Strict security: readable and writable ONLY by ubuntu (0600)
chmod 600 /opt/todo-app/server.env

Step 8: Deploy the Production Compose Contract

Place your docker-compose.prod.yml and release.env inside /opt/todo-app:

EC2 Shell · Create release.env 
# Point to your published GHCR commit SHA:
echo "IMAGE_TAG=sha-b94f0e5" > /opt/todo-app/release.env

Create or copy /opt/todo-app/docker-compose.prod.yml (matches the Stage 5 file):

/opt/todo-app/docker-compose.prod.yml 
name: todo-production

services:
  client:
    image: ghcr.io/s3nsh1-dev/docker-beginner-simulation-client:${IMAGE_TAG}
    container_name: todo-prod-client
    restart: unless-stopped
    ports:
      - "80:80"
    depends_on:
      server:
        condition: service_healthy
    networks:
      - todo-network

  server:
    image: ghcr.io/s3nsh1-dev/docker-beginner-simulation-server:${IMAGE_TAG}
    container_name: todo-prod-server
    restart: unless-stopped
    env_file:
      - ./server.env
    healthcheck:
      test: ["CMD-SHELL", "wget -qO- http://localhost:5000/health || exit 1"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 15s
    networks:
      - todo-network

networks:
  todo-network:
    driver: bridge

Step 9: Launch the Stack & Verify Production Health

Execute the deployment sequence:

EC2 Shell · Launch Stack 
# 1. Pull the pre-built GHCR images from GitHub Container Registry
docker compose --env-file release.env -f docker-compose.prod.yml pull

# 2. Launch both containers in detached mode
docker compose --env-file release.env -f docker-compose.prod.yml up -d

# 3. Check status (wait for server to show 'healthy')
docker compose -f docker-compose.prod.yml ps

# 4. Test the health endpoint through Nginx on port 80
curl -I http://localhost/api/health
Expected Verification Result

When you run curl -I http://localhost/api/health, Nginx should return:
HTTP/1.1 200 OK
Open http://<EC2_PUBLIC_IP> in your laptop's browser. The Todo app SPA will load and interact directly with your production Neon PostgreSQL database!
