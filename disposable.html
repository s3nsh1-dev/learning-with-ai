Stage 2 → Stage 3 · the same checks, now run by GitHub

Why Stage 3 runs CI

Stage 2 made the tests safe to run. Stage 3 decides when they run, gives them a clean machine, and reports the result on the pull request. The test database is temporary; the runner is the computer doing the work.

The question: If Stage 2 already containerized the client, server, and test database, and ran end-to-end tests, why add a container in a GitHub runner?
Short answer: You do not move Stage 2's containers into GitHub. GitHub starts a fresh runner for each job, and the workflow may start a separate PostgreSQL service container beside that job. The runner executes commands; the database container supplies one dependency.

What changes from Stage 2 to Stage 3

Stage 2 proves the tests; Stage 3 makes them part of the change process

Stage 2Build safe checks

Use disposable PostgreSQL data, meaningful assertions, cleanup, and a full-stack browser test.

A code changeOpen a PR

A proposed change gives GitHub a specific commit to verify. A push to main can trigger the same workflow.

Stage 3Run on clean machines

GitHub checks out the commit, installs locked dependencies, and runs jobs without relying on your laptop.

A status checkReview the result

GitHub reports each job. A repository rule can require those checks before allowing a merge.

In Stage 2, the local sequence is docker compose ... up --build --wait, run the checks, then docker compose ... down -v. The first command starts the test stack and waits for services; the last removes its containers and test volumes. Stage 3 rebuilds the needed test environment from the checked-out commit instead of carrying those local containers over.

A workflow alone does not lock the merge button. Configure the repository's branch protection or ruleset to require the relevant status checks. Without that rule, GitHub can show a failing check while still allowing someone with permission to merge.

Stage 3 is the verification gate, not image publishing or deployment. In this curriculum, Stage 4 handles publishing tested images. Stage 3 matters because a passing local run is optional and easy to forget; a required PR check makes the same checks visible at the point where the team decides to merge.

The jobs question

All three topics belong under one jobs: key

The snippets in lesson topics 02, 03, and 04 are excerpts from one workflow file. Topic 04 starts at the test-e2e: job, so the parent key is above the excerpt. It was not removed and the job is not a step inside test-server. The commands below are shortened to make the nesting visible, not a copy-paste-ready workflow.

.github/workflows/ci-cd.yml · one parent, sibling jobs 
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:                         # one shared parent
  test-client:                # topic 02
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pnpm lint
      - run: pnpm build

  test-server:                # topic 03
    runs-on: ubuntu-latest
    services:                 # Postgres belongs to this job
      postgres:
        image: postgres:16-alpine
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-timeout 5s
          --health-retries 5
    steps:
      - uses: actions/checkout@v4
      - run: pnpm test:integration

  test-e2e:                   # topic 04
    runs-on: ubuntu-latest
    services:                 # its own, separate Postgres
      postgres:
        image: postgres:16-alpine
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-timeout 5s
          --health-retries 5
    steps:
      - uses: actions/checkout@v4
      - run: |
          pnpm start &
          npx wait-on http://localhost:5000/api/health --timeout 20000
          npx playwright test

test-client

Checks the client with linting and a production build. It does not need PostgreSQL, so it has no services: block.

test-server

Runs server type checks and integration tests. Its own Postgres service gives those tests a disposable database.

test-e2e

Starts the API, waits for it, then runs browser tests. Its Postgres service is separate from the server job's database.

Each job runs on its own runner. Jobs with no needs: relationship can run in parallel. A service nested under one job is only for that job; neither job shares its database with the other. The runner starts the service before the job steps and removes it when the job ends.

The service's POSTGRES_USER, POSTGRES_PASSWORD, and POSTGRES_DB values create its test database. The step's DATABASE_URL tells the application how to connect to that database. These are disposable test credentials, not production secrets.

One detail the lesson excerpt should make explicit: the shown E2E steps start the API process, but do not show how the browser's client page is served. The Playwright configuration or another workflow step must start or provide that page. If neither does, the E2E test cannot reach the client.

Why the unfamiliar YAML is there

Read each line as a job instruction with a specific job to do

The punctuation is mostly YAML structure. The unusual values solve practical problems: preparing the machine, connecting to a temporary database, waiting for servers, or saving evidence when a test fails.

WORKFLOW START

on: and concurrency:

on: names the events that start the workflow, such as a PR targeting main or a push to main.

${{ github.workflow }} and ${{ github.ref }} are GitHub expressions. Together they group runs for the same workflow and branch or PR. cancel-in-progress: true stops an older run in that group when a newer commit makes it out of date.

MACHINE + ACCESS

runs-on, permissions, and working-directory

runs-on: ubuntu-latest asks GitHub for a hosted Ubuntu runner. Job steps run on that machine; they are not automatically inside your app's Docker image.

permissions: {} removes default token access, then a job can grant only what it needs, such as contents: read to check out code.

defaults.run.working-directory: server makes shell commands start in that folder, so steps do not repeat cd server. It affects run: commands, not actions loaded with uses:.

DATABASE SERVICE

services:, ports:, and options: >-

services: asks the runner to start a helper container for this job. The test process running on the Ubuntu host reaches the published PostgreSQL port at localhost:5432. The service's POSTGRES_* variables initialize its empty test database; the test step's DATABASE_URL points the app at it. The health check confirms PostgreSQL accepts connections; it does not run your schema migrations.

options: >- makes a readable multi-line string. GitHub passes the contained Docker flags to the service container. The >- folds line breaks into spaces and drops the final newline.

--health-cmd pg_isready asks Docker to check whether PostgreSQL accepts connections. The interval, timeout, and retry flags control those checks. GitHub waits for the service to be healthy before running steps.

TEMPORARY DATA

--tmpfs /var/lib/postgresql/data

This mounts the database's data directory in temporary memory rather than persistent storage. Test rows disappear with the service container. It is optional; it does not make this a production database, and the lesson should not promise a fixed speed-up.

INSTALLATION

uses:, with:, run:, and env:

actions/checkout@v4 checks out the commit being tested. pnpm/action-setup@v3 installs the selected pnpm version. actions/setup-node@v4 installs Node. These are reusable actions; with: supplies their inputs, such as versions and cache settings. The suffixes @v4 and @v3 select action versions.

run: executes a shell command. env: passes variables to a step, such as the test database URL. npx playwright install --with-deps chromium installs Playwright's Chromium browser and required operating-system packages. npx runs a package's command-line tool. For repeatable CI, keep these tools in the project's dependencies and lockfile.

REPEATABLE DEPENDENCIES

cache: pnpm and --frozen-lockfile

The setup action can cache downloaded packages, using the lockfile named by cache-dependency-path to choose the cache key. A cache saves download time; it is not the source of truth for versions.

pnpm install --frozen-lockfile installs the versions already recorded in the lockfile. It fails instead of silently rewriting that file when the package manifest and lockfile disagree.

START, THEN TEST

pnpm start & and wait-on ... --timeout 20000

The shell's & starts the long-running API process in the background so the same script can continue. Without it, the shell would wait for the server process to exit before starting tests.

wait-on keeps checking the health URL before Playwright starts. 20000 is a 20-second timeout in milliseconds. If the API never responds, the command fails instead of letting tests race ahead. The API and browser client must both be running before a full UI journey can pass.

KEEP FAILURE EVIDENCE

if: failure() and upload-artifact

GitHub normally skips later steps after a failure. if: failure() tells this upload step to run when an earlier step in the job has failed.

actions/upload-artifact copies the configured path: from the runner to the workflow run. Use a path the test reporter really writes. retention-days: 7 asks GitHub to keep the uploaded files for seven days.

The runner is temporary, but it is not magic: it needs checkout, runtimes, packages, a ready database, and the app processes your tests expect. The workflow spells those steps out so GitHub can repeat them for each change.
