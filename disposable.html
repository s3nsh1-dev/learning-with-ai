Acronym Reference & Core Definitions

  • GHCR (GitHub Container Registry): The container registry (ghcr.io) hosting our prebuilt, immutable client and server images.
  • OOM (Out Of Memory): The Linux kernel killer that forcibly kills running processes (like Nginx or Node) when a machine runs out of RAM during local compilation.
  • SHA (Commit Hash): The immutable cryptographic hash identifying the exact release version (e.g. sha-b94f0e5).
  • Reverse Proxy: A gateway server (Nginx) that terminates incoming HTTP connections on port 80 and routes internal API traffic to backend services.
  • Pre-flight Dry Run: Validating configuration schemas and variable interpolation (docker compose config) without launching containers.
  • Least Network Privilege: Restricting port bindings so only public-facing services (Nginx on 80) listen externally, while internal services (Express on 5000) have no public ports.

Stage 5: The Production Compose Contract & Architecture

A comprehensive architectural walkthrough of the Stage 5 deployment contract: why production pulls prebuilt GHCR images rather than building from source, how network topology restricts attack surface, and how release parameters are cleanly decoupled from database secrets.

Topic 01 · Core Concept

The Production Compose Paradigm Shift

The Golden Rule of Production Infrastructure

A production virtual machine is a RUNTIME HOST, not a compiler.
In local development, Docker Compose builds images from local source code on the fly (build: ./client). In production, the host pulls pre-verified, immutable container images directly from GitHub Container Registry (image: ghcr.io/...:${IMAGE_TAG}).

In Stage 4, your GitHub Actions CD pipeline built and published two immutable, SHA-tagged images to GHCR:
• ghcr.io/s3nsh1-dev/docker-beginner-simulation-client:sha-b94f0e5
• ghcr.io/s3nsh1-dev/docker-beginner-simulation-server:sha-b94f0e5

Stage 5 defines the Production Compose Contract. We created five key assets in docker-beginner-simulation:

Topic 02 · Operational Hazards

Why We Never Build on Production EC2

Beginner deployments often clone the entire Git repository onto an EC2 instance and run docker compose up --build. While this seems convenient, it introduces three fatal production hazards:

1. Host Memory Exhaustion (The Linux Kernel OOM Killer)

Compiling TypeScript (tsc) and bundling React with Vite requires significant RAM and CPU. On common entry-tier instances like an AWS t2.micro (1 GB RAM), a build command triggers memory spikes above 900 MB. The Linux kernel's Out-Of-Memory (OOM) killer abruptly terminates running processes to save the OS—often killing the active Nginx or Node process, causing immediate total downtime for real users.

2. Toolchain Sprawl & Attack Surface Inflation

If an EC2 server builds from source, it must permanently store Git credentials, source code files, Node.js development runtimes, npm build dependencies, and compiler toolchains. If an attacker breaches the web server, they gain instant access to proprietary source code and development tools. In contrast, a runtime host that only pulls prebuilt images requires zero source code and zero build tools.

3. Invalidation of CI Verification Guarantees

The entire purpose of Stage 3 CI is to verify that code passes linting, tests, and builds. Building on EC2 creates a new, untested binary artifact on the live server. Network blips, upstream npm package updates, or differing glibc versions can result in a broken build running on EC2 that never existed in CI.

Topic 03 · Security Boundaries

Network Topology & Port 80 Ingress

Security in containerized environments relies on Least Network Privilege. External internet traffic must never reach backend databases or Node.js application ports directly.

Complete Production Topology: Users access Nginx over public port 80. Nginx proxies /api/ internally to Express over the Docker bridge network. The server connects outbound over encrypted TLS to Neon DB. The database and backend API are completely shielded from public internet exposure.
Why Port 80 Replaces Port 3000

In local development, the client ran on 3000:80 so you could visit http://localhost:3000 without needing sudo. In production on EC2, standard web traffic enters over port 80 (HTTP). By binding 80:80, users can visit your EC2 IP address directly in their browser without typing a port number!

Topic 04 · Configuration Boundaries

Decoupling Release Tags from Runtime Secrets

A common mistake in deployment automation is dumping all configuration into a single .env file. This creates a severe operational problem: every time you deploy a new commit SHA, your automation script must edit a file that also contains sensitive database passwords. A typo or script bug could erase the database credentials!

The Clean Architectural Separation

We divide configuration into two distinct files with completely different lifecycles:
1. release.env (Dynamic Release Parameters): Contains IMAGE_TAG=sha-xxxxxxx. Changes on every deployment. Contains no secrets. Safe to log.
2. server.env (Static Runtime Secrets): Contains DATABASE_URL and PORT=5000. Configured once during server setup. Never changes between deployments. Protected with chmod 600.

1. How docker-compose.prod.yml Wires Both Files

Notice how cleanly the production Compose file references both inputs:

docker-compose.prod.yml 
services:
  client:
    image: ghcr.io/s3nsh1-dev/docker-beginner-simulation-client:${IMAGE_TAG}
    init: true
    restart: unless-stopped
    ports:
      - "80:80"
    depends_on:
      server:
        condition: service_healthy

  server:
    image: ghcr.io/s3nsh1-dev/docker-beginner-simulation-server:${IMAGE_TAG}
    restart: unless-stopped
    expose:
      - "5000"
    env_file:
      - ./server.env
    healthcheck:
      test:
        [
          "CMD-SHELL",
          'node -e "fetch(\'http://localhost:5000/api/health\').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"',
        ]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 15s

2. How Variable Interpolation Works

When Docker Compose encounters ${IMAGE_TAG} in the image: line, it resolves the value from the environment. By running:
docker compose --env-file release.env -f docker-compose.prod.yml config
Compose reads IMAGE_TAG from release.env. Simultaneously, the env_file: ./server.env directive passes DATABASE_URL and PORT directly into the Express container at startup.

Topic 05 · Pre-Flight Testing

Pre-Flight Validation & Assessment

Before deploying anything to EC2, you must verify the contract locally. Docker Compose provides a built-in pre-flight linter: docker compose config.

Terminal Verification Command 
docker compose --env-file release.env -f docker-compose.prod.yml config

This command acts as a comprehensive dry-run validator:

  • Syntax & Indentation Check: Validates YAML schema correctness.
  • Variable Resolution: Replaces ${IMAGE_TAG} with the concrete value from release.env (e.g. sha-b94f0e5).
  • Port & Network Validation: Confirms port bindings and healthcheck commands without launching any containers.
  • Rollback Simulation: You can test a rollback instantly by overriding the variable:
    IMAGE_TAG=sha-previous docker compose -f docker-compose.prod.yml config | grep image:
