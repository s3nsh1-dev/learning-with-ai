Acronyms & terms on this page

URLUniform Resource Locator — a text address that says where a service lives and how to reach it, e.g. postgres://user:pass@host:port/db.
DBDatabase — the program that stores and manages the data, here PostgreSQL.
APIApplication Programming Interface — the set of URLs (/api/todos) the server exposes for the client to call.
DNSDomain Name System — turns names into addresses; inside a Compose network, service names like test-db resolve to containers.
CIContinuous Integration — an automated service (GitHub Actions) that runs your tests on every pull request.
E2EEnd-to-end — tests that drive the real app in a browser, clicking and typing like a user.
SSL / TLSSecure Sockets Layer / Transport Layer Security — encryption for network connections; required by Neon, not needed inside a private Compose network.
YAMLYAML Ain't Markup Language — the indentation-based format Compose files are written in.
PRPull Request — a proposed change in GitHub that CI checks before merge.
tmpfsA file system held in RAM only — data written there vanishes when the container stops, leaving nothing on disk.
healthcheckA Compose feature: a command the container runs on itself so dependents can wait until it is truly ready, not just started.
pnpmPerformant npm — a fast Node package manager; your server and client use it. pnpm --dir server test runs a script inside the server/ folder.
exit codeA number every command returns when it ends: 0 means success, anything else means failure. CI and && chains read it.
pg_isreadyA small PostgreSQL tool that checks whether the database server accepts connections — used in the test-db healthcheck.
execdocker compose exec <service> <command> runs a command inside a running container — used here to inspect the server's environment.

PHASE A

Dockerized stack works — verified by hand

Goal: client + server + postgres:16-alpine containers, with the server pointed at the disposable database and you clicking through the app yourself.

Your docker-compose.test.yml copies the production server service wholesale, env_file: ./server/.env included — so tests would still hit Neon. Replace the whole file with this; the only changes are inside the server service: env_file is gone, an environment override is in, and the server now waits for the database healthcheck.

docker-compose.test.yml (replace entire file) 
services:
  client:
    build:
      context: ./client
      dockerfile: Dockerfile
    init: true
    depends_on:
      server:
        condition: service_healthy
    restart: unless-stopped
    ports:
      - "3000:80"

  server:
    build: ./server
    environment:
      DATABASE_URL: postgres://test_user:test_password@test-db:5432/todo_test_db
    depends_on:
      test-db:
        condition: service_healthy
    restart: unless-stopped
    expose:
      - "5000"
    healthcheck:
      test:
        [
          "CMD-SHELL",
          'node -e "fetch(''http://localhost:5000/api/health'').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"',
        ]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 15s
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"

  test-db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: test_user
      POSTGRES_PASSWORD: test_password
      POSTGRES_DB: todo_test_db
    ports:
      # Host port 5433 avoids clashing with a local Postgres on 5432.
      # Containers use test-db:5432; your terminal uses localhost:5433.
      - "5433:5432"
    tmpfs:
      - /var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U test_user -d todo_test_db"]
      interval: 2s
      timeout: 2s
      retries: 10

Why the URL looks like that: test-db is the service name, and inside a Compose network every service gets a DNS name equal to its name — so the server literally dials the alpine container on its native port 5432. The 5433 host mapping is only a side door for you, from outside Docker. Your db.ts enables SSL only for neon.tech / sslmode=require URLs, so no code change is needed.

Verify now (stack not needed yet): grep -n "neon" docker-compose.test.yml prints nothing, and grep -c "test-db:5432" docker-compose.test.yml prints 1.

Your current server/src/tests/api.test.ts uses console.assert, which only prints failures and still exits 0 — CI would stay green on a broken build. Replace the whole file with this: node:assert/strict throws, and a finally block deletes the test row even when an assertion blows up mid-run.

server/src/tests/api.test.ts (replace entire file) 
import assert from "node:assert/strict";
import { initDb } from "../config/db.js";
import { TodoModel } from "../models/todoModel.js";

async function runServerTests() {
  console.log("Starting server integration tests against the disposable database...");

  let createdId: number | undefined;
  let failed = false;

  try {
    await initDb();

    // 1. Create
    const title = `Test Todo ${Date.now()}`;
    const newTodo = await TodoModel.create({
      title,
      description: "Server test description",
      priority: "high",
      category: "work",
    });
    createdId = newTodo.id;
    assert.equal(newTodo.title, title, "Todo title mismatch after create");
    assert.equal(newTodo.priority, "high", "Todo priority mismatch after create");
    console.log("PASS: create todo");

    // 2. Stats
    const stats = await TodoModel.getStats();
    assert.equal(typeof stats.total, "number", "Stats total is not a number");
    assert.ok(stats.total >= 1, "Stats should include the created todo");
    console.log("PASS: fetch stats");

    // 3. Toggle
    const toggled = await TodoModel.toggle(createdId);
    assert.equal(toggled?.completed, true, "Todo should be completed after toggle");
    console.log("PASS: toggle todo");

    // 4. Delete
    const deleted = await TodoModel.delete(createdId);
    assert.equal(deleted, true, "Todo delete should return true");
    createdId = undefined; // cleanup already done — no row left behind
    console.log("PASS: delete todo");

    console.log("All server model & DB tests passed.");
  } catch (err) {
    failed = true;
    console.error("Server integration test failed:", err);
  } finally {
    // Runs on success AND failure: never leave test data behind.
    if (createdId !== undefined) {
      await TodoModel.delete(createdId).catch(() => {});
    }
  }

  process.exit(failed ? 1 : 0);
}

runServerTests();

PHASE B

Introduce Playwright against the Dockerized stack

Goal: the browser tests you already have in client/e2e/todos.spec.ts drive the real composed app instead of the Vite dev server.

The config currently targets localhost:5173 (Vite dev). Two values change: baseURL moves to the nginx container on :3000, and the webServer block becomes a Compose bootstrap so standalone runs also work. Your specs in e2e/todos.spec.ts need zero changes — they use relative URLs, so they follow baseURL.

client/playwright.config.ts (replace entire file) 
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',
  fullyParallel: false,
  forbidOnly: !!process.env.CI,
  retries: 1,
  workers: 1,
  reporter: 'list',
  use: {
    baseURL: 'http://localhost:3000', // the dockerized client (nginx)
    trace: 'on-first-retry',
    headless: true,
  },
  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] },
    },
  ],
  webServer: {
    // Fallback bootstrap: if the stack is already up (Phase A), Playwright
    // detects the URL and skips this. `up -d --wait` is idempotent.
    command: 'docker compose -f ../docker-compose.test.yml up -d --wait',
    url: 'http://localhost:3000',
    reuseExistingServer: true,
    timeout: 120000,
  },
});

First run only: make sure a Chromium binary exists for Playwright to drive (already done on this machine for the learning project, but the client has its own Playwright version):

terminal · first time only 
pnpm --dir client exec playwright install chromium
Verify: grep -n "3000" client/playwright.config.ts shows both the baseURL and webServer url on port 3000, and no 5173 remains.

There is no package.json at the repo root yet — create it. The chain: bring the stack up, run the server suite, run the browser suite, then always tear down. The teardown is joined with ; instead of && so it runs even when a test suite fails — a crashed test can never leave containers behind.

package.json (create at repo root) 
{
  "name": "docker-beginner-simulation",
  "private": true,
  "scripts": {
    "test:e2e": "docker compose -f docker-compose.test.yml up -d --wait && DATABASE_URL=postgres://test_user:test_password@localhost:5433/todo_test_db pnpm --dir server test && pnpm --dir client run test:e2e ; docker compose -f docker-compose.test.yml down -v"
  }
}

Read the chain as the Stage 2 story in one line: ephemeral environment up → integration tests against it → full-stack browser tests against it → demolition, always.

Verify: npm run (at root) lists test:e2e, and node -e "JSON.parse(require('fs').readFileSync('package.json'))" prints no error — valid JSON.

Running it twice from a clean state is the repeatability proof: the tmpfs database is fresh RAM each time, so a second green run cannot be explained by leftover data.

terminal · repo root — the repeatability drill 
docker compose -f docker-compose.test.yml down -v
npm run test:e2e

# afterwards: prove nothing was left behind

Expected per run: server suite PASS lines, then the Playwright list reporter showing the todos.spec.ts tests passing against http://localhost:3000. After the runs: ps prints an empty header (no containers), and no project volumes remain.

If Playwright fails to connect: the stack from Phase A may still be running with old server wiring. Run docker compose -f docker-compose.test.yml down -v once, then npm run test:e2e — up --wait rebuilds with the Step 1 config.
