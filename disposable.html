Stage 4, publishing images

Build it here.
Pull it there.

A Docker image is the packaged application. A container registry stores that package so GitHub Actions, a developer's laptop, or the EC2 server can upload and download it.

Short answer

GHCR was chosen because this project already uses GitHub. Actions can publish with a short-lived, narrowly permissioned token, and the image package can live beside its source repository. Docker Hub can store the same image. The project could use it instead.

First, the basic idea

What is a container registry?

Think of the registry as a remote package store. It does not run the application. It keeps published images and serves them to software that asks for a particular image.

Image: the thing you build

A Dockerfile describes how to assemble the application and its runtime files into an image. The image is made of a config and filesystem layers. A running container is created from an image.

In this project, the client and server are separate images because they are separate app parts with different build and runtime needs.

Registry: where you publish it

A registry accepts image uploads, stores image data, and lets authorized users download it later. It usually organizes images into repositories and uses tags or digests to identify versions.

GitHub Actions builds and pushes the images. EC2 later authenticates and pulls them. The registry is the handoff point between those two machines.

Same package, different address

GHCR or Docker Hub?

Select a destination. The build and Docker image format stay the same. The image name, login, access settings, and registry account change.

Why this project uses GHCR

The repository and workflow already live on GitHub. A publishing job can use its job-scoped GITHUB_TOKEN with packages: write instead of storing a Docker Hub password in repository secrets. 

ghcr.io/s3nsh1-dev/docker-beginner-simulation-client:<commit-sha>

Pick based on the project

When would you choose each one?

Neither service is inherently the right registry for every team. Compare account ownership, who needs access, automation, pricing, storage rules, and image pull limits.

Question GHCR Docker Hub Another registry

Your cloud provider or company already manages a registry, such as Amazon ECR for an AWS-centered setup.

Can Docker pull it? Yes, after login if the package is private. Yes, after login if the repository is private. Yes, after using that registry's authentication method.
Moving from GHCR to Docker Hub would not mean rewriting the Dockerfile. You would change the image name, configure a Docker Hub repository, change workflow login credentials, update the server's pull address, and grant the right people access.

The Stage 4 path

What happens after a merge?

This project publishes the client and server images after trusted checks pass on the merged commit. A pull request can run tests, but it should not publish production packages.

Git names the commit

A commit has an object ID, often called its commit SHA.

Actions checks it

Tests and builds must pass before the publish job runs.

Build and push

Buildx packages each app part and uploads it to GHCR.

Registry records it

Tags point to manifests, which describe image config and layers.

EC2 pulls it

The host downloads the selected image and starts its container.

These are two different packages

ghcr.io/s3nsh1-dev/docker-beginner-simulation-client:<full-commit-sha>
ghcr.io/s3nsh1-dev/docker-beginner-simulation-server:<full-commit-sha>

The client and server use the same source commit value in their tags, but each name points to a different image. EC2 can pull both tags and run that release together.

What the registry stores

What is an image manifest?

A manifest is a small data record that tells a container tool which config and filesystem layers make up one image for one platform.

It points to the pieces

The registry stores image data as blobs. The manifest lists descriptors for the image configuration and its layers. Each descriptor includes a content digest and size, so the client knows what to request and can check what it received. 

{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": { "digest": "sha256:..." },
  "layers": [
    { "digest": "sha256:..." },
    { "digest": "sha256:..." }
  ]
}

A pull is a lookup, then downloads

  1. Docker asks the registry for an image by name and tag.
  2. The registry resolves that tag to a manifest or image index.
  3. Docker downloads the referenced config and missing layers.
  4. Docker checks their digests and assembles the image locally.
A multi-platform image can start with an image index, which points to separate manifests such as linux/amd64 and linux/arm64. Docker selects the one that matches the machine. That is why Stage 4 mentions multi-platform tagging.

Trace a release to source

What is a Git commit SHA?

It is the object ID Git uses to identify a commit. It identifies that commit record, which includes the project tree and commit metadata, not merely a filename or a Docker image.

Get it from your checkout

git rev-parse HEAD
git show -s --format='%H%n%s' HEAD

HEAD means the commit currently checked out. The first command prints its full object ID. The second prints the ID and the commit subject line. A short form such as 8e91c2d is easier to read, but use the full value for an unambiguous release tag.

Why put it on the image tag?

If the image tag includes the source commit ID, a deploy log gives you a direct lead back to the code change. You can ask, "Which commit built the client running on EC2?" and inspect that commit in GitHub.

A tag like latest does not answer that question by itself because it usually gets moved to a newer image.

A commit tag and an image digest identify different things

IMAGE_TAG="$(git rev-parse HEAD)"
docker pull "ghcr.io/s3nsh1-dev/docker-beginner-simulation-client:${IMAGE_TAG}"

# A registry can also address the exact image content by digest:
docker pull "ghcr.io/s3nsh1-dev/docker-beginner-simulation-client@sha256:<manifest-digest>"

The commit SHA identifies source history. The sha256:... image digest identifies image content. The build connects them through the tag and image metadata.

A SHA-looking tag is not automatically immutable. Docker tags are names that can be reassigned unless registry policy prevents it. A commit-SHA tag is a useful release convention, but the image digest is the content-derived identifier. Stage 4's "immutable SHA tag" means "tagged to a specific source commit"; do not assume the registry rejects someone moving that tag.

Questions that come up while wiring it

A few practical clarifications

These are the distinctions that make registry setup easier to troubleshoot.

Why did ghcr.io open a GitHub Actions page?

Visiting https://ghcr.io in a browser currently redirects to GitHub's Actions feature page. That root address is not the registry's package browser. Docker tools use ghcr.io as the registry hostname with a full image path, such as ghcr.io/s3nsh1-dev/docker-beginner-simulation-client:tag.

Actions and GHCR are separate services. Actions runs the workflow; GHCR stores and serves the image. The direct container registry docs explain the package service.

Is GHCR outdated, or does GitHub Actions replace it?

No. Current GitHub documentation still describes publishing images to GitHub Packages and container registries. Actions is one way to automate a build and push. GHCR is one place to store the result.

Does the registry build the image?

Usually the CI runner builds it from the Dockerfile and pushes the finished image. Some registry services also offer automated builds, but this project builds in GitHub Actions. The registry's job here is storage and distribution.

What does the workflow token actually allow?

The publishing job requests only the permissions it needs, such as contents: read to check out source and packages: write to publish the image. Pull requests should not get that publish permission. EC2 uses separate, read-only registry credentials to pull private images.

Back to the lesson

What Stage 4 is asking you to wire up

Stage 4 is the publish step after Stage 3's checks. It does not deploy the app to EC2 yet. Later stages configure the host to pull and run these images.

GitHub Actions job
  • Run only for a trusted commit after the checks pass.
  • Grant contents: read and packages: write to the publish job.
  • Log in to ghcr.io with that job's GITHUB_TOKEN.
  • Build and push separate client and server images, tagged with the commit ID.
Later, on EC2
  • Log in with credentials that can read the private packages.
  • Set the release tag to the commit that should run.
  • Use Docker Compose to pull both matching images.
  • Start the services and check application health.

For the exact GitHub workflow syntax, the GitHub publishing guide covers GHCR and Docker Hub. The Docker Hub repository guide explains Hub repositories. The OCI manifest spec defines image manifests. The Git object guide explains Git object IDs.

The complete capstone route

From app code to a checked release on EC2

Follow the numbered parts in order. Each diagram keeps the checkpoints visible, including the pull request stop, both image builds, the host's private files, the health check, and rollback. On a narrow screen, scroll inside a diagram rather than losing a step.

01 / Verify a proposed change

Source code enters the pull request gate

Client, server, and end-to-end checks can run in parallel. Their results join at one merge decision.

02 / Publish the approved commit

Checks unlock two separate GHCR images

A push to main runs the checks again. The publish job depends on all of them and tags both images from the same source commit.

03 / Send the release to EC2

Deploy the exact two tags, not source code

The deploy job serializes releases, verifies the SSH host, and tells EC2 which already-built commit to run.

04 / Prove the release is healthy

Route traffic, check health, restore if needed

Deployment is not done when containers start. The workflow checks the public health route and has a previous SHA to restore if the new release fails.
