02 / Build versus runtime · questions 1, 4, 5 & 7

Source goes into the build. Output goes into the final image.

For your production-shaped frontend, choose the built app at runtime. You still need source earlier so something can produce that built app.

An original source file is what you edit. A build artifact is output a tool produces, such as dist/index.html and dist/assets/*.js. Building prepares files. Running starts a long-lived process that uses them.

Why the earlier frontend and backend examples looked different

The frontend example kept source and build together so Vite could serve the build with preview. The backend example assumed you had already built dist/ outside Docker and would copy it in. Those were two different build locations, not a rule that frontends need source at runtime and backends do not.

Both are possible. A common production flow builds inside Docker using separate stages. Another builds in an automated pipeline and copies the ready output into an image. For this exercise, use the first flow. Docker builds your frontend without relying on a local dist/.

Your two backend choices leave out a useful third choice: copy source into a build stage, run the build there, then put the output and required runtime dependencies in the final image. Production usually runs prepared code without a development watcher. If the backend were plain JavaScript with no build step, running that JavaScript directly would also be valid.

You are deliberately leaving the server Dockerfile alone. That is fine. We are choosing the frontend pipeline now, not making every service production-ready at once.

03 / Files need a server · questions 2 & 3

A folder cannot listen on a port

dist/index.html is a file. You need a running HTTP server to answer requests such as GET / and send that file to the browser.

Opening the file directly gives you a file:// URL. It does not start a server. A Vite build can use asset paths such as /assets/..., which expect a web root. Module loading and other browser rules also differ for local files. Serve the folder over HTTP instead.

Does npm run start do something special?

A package script is a named command. It does what package.json says, not what its name sounds like. Your client has no start script. Adding one would be a convenience, not the missing mechanism that gives files a port.

For a backend, node dist/index.js directly starts the program. Your server defines "start": "node dist/index.js", so pnpm run start starts the same program through that script. Both are normal. The process underneath matters more than whether a package manager launches it.

04 / Recipe · frontend only

Build once. Start a file server.

Use Node to prepare the app. Use Nginx, pronounced "engine x", to answer HTTP requests with the prepared files.

You do not need to learn reverse proxies or load balancing here. Nginx is simply the HTTP file server from the previous topic. It sends HTML, JavaScript and CSS to the browser. It does not execute your React app; the browser does that.

You do not need to install Nginx on your computer. Docker gets it from the final stage's base image.

Proposed replacement · client/Dockerfile
FROM node:24-bookworm-slim AS build
WORKDIR /app

RUN corepack enable && corepack install --global pnpm@12.4.2
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile

COPY . .
RUN pnpm run build

FROM nginx:stable-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist/ /usr/share/nginx/html/

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
RUN pnpm install
Installs packages inside the build stage. It does not create your app's dist/. Build tools are needed here, so do not use --prod for this installation.
RUN pnpm run build
Creates /app/dist/ while Docker builds the image. A RUN instruction is not the command that keeps a container running later.
FROM nginx:stable-alpine
Starts the final stage from the official Nginx image. The earlier Node filesystem does not carry over automatically.
COPY --from=build ...
Copies the output from the named build stage. Docker does not need a dist/ folder on your machine.
EXPOSE 80
Documents the container's listening port. It does not publish that port to your machine. docker run -p will do that.
CMD ["nginx", "-g", "daemon off;"]
Starts Nginx when a container starts. daemon off; keeps it in the foreground so the container has a running main process. The official image already uses this command; it is written here to make startup explicit.

This is a production-shaped static frontend, not a complete production deployment. We are leaving HTTPS, deployment automation, strict image pinning and the API address for later.

05 / One new file · no package-script changes

Tell the server where the files are

Create client/nginx.conf. It selects the listening port and the folder Nginx serves.

New file · client/nginx.conf
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
listen 80;
Accept requests on port 80 through the container's IPv4 interfaces. It is not restricted to container loopback.
server_name _;
A conventional placeholder name. This is the only server block in the replacement config, so requests for localhost use it. The underscore itself is not a magical catch-all.
root and index
Read files from this folder. For a request to /, return index.html. The Dockerfile copies the contents of dist/ into this folder.
try_files $uri $uri/ /index.html;
Try a matching file or directory first. If neither exists, return index.html. This supports browser-side app routes when a user reloads a URL. It does not forward API requests to the backend.

Keep your existing client/.dockerignore. Excluding host dist/ is still correct. The first Docker stage makes a new one. Do not exclude the new nginx.conf, because the final stage copies it from the build context.

You do not need to add a client start script. The Nginx image supplies the executable, and its CMD starts the server.

06 / Network boundary · question 6

"Only me" versus "all my interfaces"

A server chooses both a port and which network addresses it will accept connections through. That choice is called its listening or binding address.

127.0.0.1 is IPv4 loopback. It means "this environment talks to itself." Inside a container, it means that container, not your computer.

0.0.0.0 is the wildcard listening address for all IPv4 interfaces in that environment, including its container network interface. It is not the address you type into the browser and it does not mean port zero.

How that applies to each server

For a Vite server inside a container, --host 0.0.0.0 changes the listening address. In our Nginx config, listen 80; already means all IPv4 addresses on that port, so no Vite flag is needed.

You still visit http://localhost:3000. Your browser's localhost means your computer. Docker forwards that connection into the frontend container.

A wildcard listener inside the container does not by itself publish a machine port. For a local-only lab, you can use -p 127.0.0.1:3000:80 to limit the published host port to your own computer. The container server still needs its all-interface listener.

Vite host setting Nginx port-only listener Docker port publishing

Remember the two sidesInside the container, accept traffic on its interface. Outside it, publish the port you want to visit.

09 / Build output is tool-specific · question 8

A build folder is not a promise of bundling

Your idea describes what a bundler often does. It does not describe every tool that creates a dist/ folder.

A compiler translates code. A bundler follows imports and combines required code into deployable files, often split into several chunks. A tool can do both, but the folder name does not tell you which happened.

Your frontend · Vite

Its build includes the required browser-side library code in the generated JavaScript assets. Nginx sends those assets. The final frontend container does not need your project's node_modules/.

Your backend · tsc

Its build translates TypeScript to JavaScript without bundling the imported packages. Node still needs those packages when the compiled JavaScript runs.

Your existing server/dist/index.js actually begins with these lines:

Evidence · current compiled server output
import express from 'express';
import cors from 'cors';

The Express implementation is not pasted into this file. At runtime, Node resolves those imports to installed packages, normally under node_modules/. That is why a backend runtime commonly needs the built JavaScript and production dependencies.

pnpm install prepares dependencies. pnpm run build prepares app output. With your current backend toolchain, neither replaces the other.

A backend bundler could include many dependencies, but some can remain external, especially native packages. Do not assume that every dist/index.js is a self-contained program.

You asked to postpone backend container changes. This explains the dependency question only; it is not another instruction to rebuild the server now.

10 / Failure behavior · question 9

No retry limit unless you choose one

unless-stopped does not have a maximum retry count. A recurring failure can keep the container restarting rather than ending after a fixed number of attempts.

PolicyBehavior after an exitRetry limit
"no"Leave it stopped. This is the default.No retries.
on-failure:3Retry a nonzero exit, up to 3 times.Three restart attempts, after the initial attempt.
unless-stoppedRestart automatically; preserve an intentional stop across Docker restarts.No configured maximum.

A restart launches the same configured command again. It does not repair a missing file, bad config or dependency. A retry can help with a temporary outage; it cannot fix a permanent mistake in your image.

My earlier suggestion to omit restarts was about making the first test easy to observe. It was not because restarts erase the error. Logs remain available. Docker's restart policy has lifecycle rules too, so do not treat the policy name as a complete guarantee for every startup failure.

If a Compose client fails · inspect before down

Inspect logs before deleting the container. In Lab A, --rm removes the stopped test container, so keep the terminal error output if it fails.

Keep restart policy out of these two lab runs. Once startup works, you can add a policy deliberately. If you want a finite experiment, Compose supports restart: on-failure:3.

11 / Filesystem vocabulary · questions 10 & earlier volume doubts

The host is the machine running Docker

For a local Docker Engine on your Linux computer, your computer is the host. The container has its own filesystem view inside that host.

A bind mount makes a host folder visible at a container path. In ./client:/app, ./client is on the host and /app is the path inside the container.

If Docker uses a remote daemon, the host is that remote machine. Docker Desktop runs the daemon in a virtual machine and handles sharing your computer's folders into it. "Host" is about where Docker runs, not about a web-hosting company.

Why a source mount can hide installed packages

Suppose the image contains /app/src and /app/node_modules. Mounting a host folder over /app changes what the container sees at that path. It sees the host folder, not a merge of the host folder and the image folder.

If that host folder does not have usable dependencies, the image's dependencies are hidden. They have not been deleted from the image.

Explanation only · a development setup, not this lab
volumes:
  - ./client:/app
  - client_deps:/app/node_modules

The first entry is a bind mount for live source edits. The second puts a Docker-managed volume at the more specific dependency path. A complete Compose file would also declare client_deps in its top-level volumes: section. A fresh, empty volume normally receives files already present there in the image. An existing volume keeps its own contents, so it can become stale after dependency changes.

Installing packages creates a node_modules directory. That does not automatically create a Docker volume. Volumes are storage you request separately, and they can outlive containers. They are not important because the folder has a special name; they matter because their contents affect what the app can run.

Use no app mounts or dependency volumes in this frontend lab. The built files are already inside the image. Edit source, rebuild the image, and recreate the container.

12 / Optional command reading · question 11

The second command does not start the app

Your interpretation of the first command was right. The second checks JavaScript syntax without executing the program.

Previous suggestion · from the monorepo root

pnpm --dir server run build
--dir server tells pnpm to act as if it started in the server/ directory. run build looks up that folder's build script. In your backend it runs tsc, which creates compiled JavaScript output.
