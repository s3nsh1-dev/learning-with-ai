Notes part 1 · explanation

80 is the host port. 3000 is the container port.

Mostly correct

I read your note as saying that EC2 port 80 maps to the web container's port 3000. That direction is correct. The handwritten number also looks like 5000 in one place; the lesson uses 3000.

services:
  web:
    ports:
      - "80:3000"

Docker forwards connections arriving at host port 80 to port 3000 inside web. The web server must actually listen there, usually on 0.0.0.0:3000. This mapping does not change the server's listening port.

Your EXPOSE location is right: EXPOSE 3000 belongs in a Dockerfile. It documents a port; it neither publishes it nor starts a server. Publishing works without that instruction. AWS security-group access remains a separate setting.

Small spelling fixes for your transcription: use services, ports, and networks, with the shown casing. Topic 8 uses an existing image:; build: ./web instead asks Compose to build from that directory.

Notes part 2 · explanation

One input variable. Two places that use it.

The variable reading needs a correction

${DB_PASSWORD:?Set DB_PASSWORD} refers to one variable. Set DB_PASSWORD is an error message, not a second variable.

Before creating containers, Compose replaces ${...} with a value. This is called interpolation. Here :? means “stop with this message if the value is missing or empty.”

# .env beside compose.yaml, example value only
DB_PASSWORD=example123

# api.environment in the lesson
DATABASE_URL: "postgresql://todo:${DB_PASSWORD:?Set DB_PASSWORD}@db:5432/todo"

# db.environment in the lesson
POSTGRES_PASSWORD: "${DB_PASSWORD:?Set DB_PASSWORD}"

For this example, API receives DATABASE_URL=postgresql://todo:example123@db:5432/todo. DB receives POSTGRES_PASSWORD=example123. A shell environment value can override the value from .env.

DB does not send its environment to API. Compose configures each separately. Nor does every entry in .env automatically enter every container.

URL pieceMeaning
postgresql://PostgreSQL connection scheme
todo:example123Database user and password
@db:5432DB service hostname and listening port
/todoDatabase name

The username and database name happen to both be todo. They are different settings. The URL uses them as text, not as references to variables named POSTGRES_USER or POSTGRES_DB.

References: required-value syntax, .env and interpolation.

Notes parts 2–3 · explanation

The database image reads those names.

Your startup intuition is right

Those environment values help the PostgreSQL container initialize. But the names in topic 8 are correct. They are POSTGRES_USER, POSTGRES_PASSWORD, and POSTGRES_DB, without QL.

db:
  image: postgres:17
  environment:
    POSTGRES_USER: todo
    POSTGRES_PASSWORD: "${DB_PASSWORD:?Set DB_PASSWORD}"
    POSTGRES_DB: todo

The official image's startup script uses these settings when its data directory is empty. It creates the initial administrative user, sets that user's password, and creates the named database. POSTGRES_DB is therefore used, even though your own API code never reads that variable.

API receives its own connection setting, DATABASE_URL. Its database library uses that URL to log in to the database that DB initialized. Your API code must be written to read this setting.

These values do not reset an existing database on each launch. If the saved database already exists, editing POSTGRES_PASSWORD does not change its actual password.

The volume explains why data survives

volumes:
  - pgdata:/var/lib/postgresql/data

This mounts Docker-managed storage named pgdata at PostgreSQL 17's data directory. Replacing the DB container can reuse those files. The volume keeps data outside that container's writable layer; it is still stored on the host, so it is not a backup against losing the host's disk.

References: PostgreSQL image initialization, volume lifetime.

Notes parts 1–4 · teach + explanation

Declare the networks. Then attach services.

Your DB membership explanation is correct

DB joins api_db so API and DB can communicate. API joins two networks because it needs to communicate with both web and DB.

services:
  web:
    networks: [web_api]
  api:
    networks: [web_api, api_db]
  db:
    networks: [api_db]

networks:
  web_api:
  api_db:
    internal: true

At the bottom, top-level networks: declares the networks for this project. Under a service, networks: attaches that service's containers to the named networks. Neither declaration alone does both jobs. The square brackets are a YAML list.

web_api and api_db are names we chose. Docker does not interpret the words to decide who belongs. The service-level lists decide membership. A hyphen is also legal in a chosen name, but spelling must match everywhere.

For this single-host setup, Docker creates virtual bridge networks inside EC2. Think of each bridge as a virtual Ethernet switch. Containers attach through virtual interfaces. This gives them a packet path; it does not make them share one network namespace.

Network membership permits communication both ways. The API application receives a web request and makes a separate database connection. Joining two networks does not automatically make API forward arbitrary packets between them.

References: network declaration and attachment, bridge networks.

Notes part 3 · teach

Running is earlier than ready.

A new DB container can be running while PostgreSQL is still starting. The health check repeatedly asks whether PostgreSQL is accepting connections.

healthcheck:
  test: ["CMD-SHELL", "pg_isready -U todo -d todo"]
  interval: 5s
  timeout: 3s
  retries: 10

CMD-SHELL runs the command through a shell inside DB. pg_isready is PostgreSQL's readiness tool. -U todo supplies a username and -d todo supplies a database name. With no -h, this image normally checks the local server through its Unix socket.

The interval sets the spacing between checks. Timeout limits each check to three seconds. Ten consecutive failures mark the container unhealthy. A successful check marks it healthy; this is not “wait for ten successes.”

# Inside api's service definition
depends_on:
  db:
    condition: service_healthy

Compose waits for DB's health check to pass before starting API. By contrast, web's depends_on: [api] waits for API to start, without checking whether it is ready to serve HTTP.

What a green check does not prove

pg_isready tests server readiness. It does not prove that API's password works, that API can reach DB over its network, or that your app's tables exist. An actual query from API checks those additional steps.

Later failures still need application retries. A plain Docker health check does not restart an unhealthy container by itself.

References: Compose startup order, pg_isready, health-check settings.

Notes part 4 · explanation

EC2 contains the networks. They are not one shared network.

Refine your EC2 → Docker → container sketch

It correctly places Docker networking inside EC2. But there are two separate virtual networks here, and API attaches to both. A container is not automatically connected to every Docker network on EC2.

networks:
  web_api:
  api_db:
    internal: true

internal: true makes api_db externally isolated. DB can talk to API on that network, but it does not get an ordinary outbound internet path through it. The empty web_api: definition uses the normal network defaults.

API also joins web_api, so API can still have outbound internet access through that other network. Marking one network internal does not isolate every container attached to it from all other networks.

These are different controls: network membership connects containers, internal controls external connectivity of that network, and ports publishes a service through the host. In the lesson, only web publishes a port.

Connection in this setupReason
web ↔ apiShared web_api network
api ↔ dbShared api_db network
web → db directlyNo shared network
Internet → webPublished host port, subject to AWS and host access rules

Notes part 5 · explanation

First ask where the code is running.

Your image-to-container sequence is right

You build images using Dockerfiles, then Compose uses images to create containers with the configured connections. The correction is in the next step: frontend JavaScript downloaded from web runs in the user's browser.

In this lesson, browser code calls fetch('/api/todos'). It reaches the public EC2 address. The web server then proxies the request to http://api:8000/todos. Browser code cannot normally use Docker's private api hostname.

DNS gives an address. Networking carries packets.

Your phrase “namespace is changed to Docker IP” needs a small replacement: Docker DNS resolves the service name to a container IP. It does not change a namespace or transport the HTTP request.

For web to reach API, web needs the shared network path, a resolved destination address, and an API process listening on the right interface and port. DNS helps find the address. It cannot make a missing connection or stopped server work.

API connects to db:5432 with a PostgreSQL driver, not HTTP fetch. DNS resolves db, the shared api_db network carries packets, and PostgreSQL checks the connection credentials.

A corrected version of your explanation

Compose attaches web and API to one network, and API and DB to another. It publishes EC2 port 80 to web port 3000. Browser requests reach web through the public address. Web proxies API requests over web_api. API opens a database connection over api_db. Docker DNS lets the containers use service names instead of fixed IP addresses.

Check yourself: would EXPOSE 8000 let my browser use api:8000?

No. EXPOSE is image metadata. Your browser still cannot resolve that private Docker name. In this setup it calls the public /api/todos route.

Check yourself: does a passing DB health check prove my tables exist?

No. It means the server is accepting connections. Your migration creates the application's tables; an application query verifies they can be used.

Topic 8 · build the web image

Build the frontend. Give the result to Nginx.

This example assumes a React/Vite frontend with a build script that runs vite build and produces dist/. These are example application files, not this learning repo's own setup.

todo-stack/
  compose.yaml
  .env
  web/
    Dockerfile
    .dockerignore
    nginx.conf
    package.json
    package-lock.json
    index.html
    src/                 # your frontend source
  api/                   # next topic

web/Dockerfile

# Stage 1: turn frontend source into browser files
FROM node:24-bookworm-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: the image we actually run
FROM nginx:stable-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist/ /usr/share/nginx/html/
EXPOSE 3000
CMD ["nginx", "-g", "daemon off;"]

FROM starts a build stage from a base image. The first stage has Node and npm to build your frontend. WORKDIR /app sets the working directory inside that stage. Copying the package files first lets Docker reuse the dependency-install step when only your source changes.

npm ci installs the dependencies described by your lockfile, including the build tools. It requires package-lock.json to match package.json. COPY . . then copies the remaining web files into /app, and npm run build creates the browser assets.

This is a multi-stage build. It does not create two running Compose services. Compose starts one web container from the final image. RUN executes during the build; CMD records the default command for container startup. daemon off; keeps Nginx in the foreground.

The configuration that actually opens port 3000

Save this as web/nginx.conf. The Dockerfile copies it into Nginx's configuration directory.

server {
    listen 3000;
    root /usr/share/nginx/html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://api:8000/;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

listen 3000 makes Nginx accept connections on port 3000. EXPOSE 3000 only documents it. Compose's "80:3000" publishes it through host port 80.

Nginx serves files from root. For a frontend route without a matching file, try_files falls back to index.html. Requests starting with /api/ instead go to API. The trailing slash on proxy_pass turns /api/todos into /todos.

Keep local files out of the build

Save this as web/.dockerignore:

node_modules
dist
.git
.env
.env.*

The browser still calls fetch('/api/todos'). No database password belongs in these frontend files. This example uses the same public origin, so it needs no environment-specific API hostname baked into the frontend.

The base-image tags shown here can receive updates. A release can pin tested digests for an exact rebuild. With this simple Nginx configuration, restart web after replacing API so it resolves API's current address.

References: multi-stage builds, npm ci, Vite builds, Nginx image, proxy path handling.

Topic 9 · build the API image

Keep Node in the API image. It runs your server.

The stack in these examples

The original lesson uses PostgreSQL, not MongoDB. Here we choose React, Express, and Node to fill in its unspecified application pieces. Together with PostgreSQL, this is often called PERN. Nginx serves the React build and forwards API requests.

Assume a plain JavaScript Express API with server.cjs as its entry file and express and pg listed under dependencies. Its package-lock.json comes from installing those dependencies with npm.

api/
  Dockerfile
  .dockerignore
  package.json
  package-lock.json
  server.cjs
  # Other route or database files your server imports

api/Dockerfile

FROM node:24-bookworm-slim
WORKDIR /app
ENV NODE_ENV=production

COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --chown=node:node . .

USER node
EXPOSE 8000
CMD ["node", "server.cjs"]

This API runs JavaScript directly, so it needs no frontend-style build step. Node remains in the final image because it executes your server throughout the container's lifetime. A TypeScript API would need a compilation step before running the resulting JavaScript.

InstructionPurpose here
ENV NODE_ENV=productionSets the default runtime mode for libraries that read it.
RUN npm ci --omit=devInstalls locked runtime dependencies; omits development-only packages.
COPY --chown=node:node . .Copies API files into /app and gives the image's node user ownership of those copied files.
USER nodeRuns the startup command as the base image's non-root node user.
CMD ["node", "server.cjs"]Starts /app/server.cjs when the container starts.

Save the same ignore rules as topic 8 in api/.dockerignore. In particular, excluding node_modules prevents your laptop's installed packages from overwriting the ones installed inside the image. Excluding .env keeps local configuration out of the image.

The application supplies the actual behavior

The Dockerfile cannot create an HTTP route or database connection. These are the relevant lines in your Express application, shown as an excerpt:

const express = require('express');
const { Pool } = require('pg');
const app = express();

const pool = new Pool({
  connectionString: process.env.DATABASE_URL
});

app.get('/todos', async (req, res) => {
  try {
    const result = await pool.query(
      'SELECT id, title FROM todos ORDER BY id'
    );
    res.json(result.rows);
  } catch (error) {
    res.status(503).json({ error: 'Could not load todos' });
  }
});

app.listen(8000, '0.0.0.0');

app.listen opens the port. EXPOSE 8000 documents it. The pg library reads the connection string you pass to it and uses PostgreSQL's protocol to talk to DB. This excerpt assumes your migration already created todos with id and title columns. It illustrates the connection; a complete API also needs its authentication, logging, and retry behavior.

Compose adds the password when API starts

Keep the existing api.environment.DATABASE_URL in Compose. Do not put the password in a Dockerfile ENV instruction. The root .env feeds Compose's substitution; your container receives the resulting setting through environment:.

Connect these Dockerfiles to the existing Compose file

In the example app's compose.yaml, replace the two registry-placeholder image lines and add build as below. Keep all the original ports, environment, networks, dependencies, DB settings, and volumes. This is a fragment, not a replacement for the whole file.

services:
  web:
    build: ./web
    image: todo-web:local
    # Keep web's other settings from topic 8 in index.html

  api:
    build: ./api
    image: todo-api:local
    # Keep API's other settings from topic 8 in index.html

build: ./web selects the directory Docker may copy from, called the build context, and uses its Dockerfile. image: todo-web:local names the built result. API works the same way. These names identify local images; they do not upload anything to a registry.

# From the example app's todo-stack directory
docker compose up -d --build

This builds the application images and starts the services. Your existing DB image remains postgres:17; it needs no custom Dockerfile for this example. If images are built elsewhere, push them to your registry and use those image names on EC2 as the original lesson describes.

Why does web have two FROM lines while API has one?

Web uses Node to produce static files, then needs only Nginx to serve them. This plain JavaScript API needs Node at runtime and has no separate compilation output to copy. The number of stages follows the application's needs.
